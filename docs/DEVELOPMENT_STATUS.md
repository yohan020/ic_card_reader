## 완료: 개찰구 입장 후 이동 중 상태

- 실측한 Tokyo Metro 입장·하차 fixture를 바탕으로, 일반 이용 이력 `090F`를 읽은 뒤 게이트 이력 서비스 `108F`와 입장 상태 서비스 `10CB`의 첫 블록을 추가로 읽는다. 이 서비스 원본 데이터는 화면·로그·저장소·서버에 남기지 않고 현재 스캔 중 판정에만 사용한다.
- 최신 `108F` 이벤트가 입장값 `A0`이고 역 코드 쌍이 `10CB`의 입장 코드와 일치할 때만 홈에 `현재 이동 중` 카드와 입장역을 표시한다. 하차 이벤트 `20`, 서비스 읽기 실패, 코드 불일치, 역명 후보 모호·미등록 시에는 오탐을 피하기 위해 카드를 표시하지 않는다. 일반 이용내역 `090F`가 비어 있어도 이 조건을 만족하면 이동 중 상태만 표시한다.
- `108F`·`10CB`에는 `090F`처럼 정규화된 지역 코드가 없으므로, 앱은 노선·역 코드 조합이 전체 역 데이터에서 유일할 때만 역명을 확정한다. Tokyo Metro의 `上野 → 赤坂`, `赤坂 → 新御茶ノ水` 입장·하차 흐름을 단위·위젯 테스트로 고정했다. Android 실기기에서 2026-08-26 Tokyo Metro 긴자선 `上野` 입장 상태와 2026-08-28 JR 동일본 도호쿠선 `上野` 입장 상태가 모두 `현재 이동 중` 카드로 표시되는 것을 확인했다. 도에이·사철은 실기기 결과를 추가로 확인한다.

## 완료: 한국어 역명 보조 표기

- Wikidata CC0 구조화 데이터로 보수적으로 생성한 한국어 역명 asset을 반영했다. 앱은 실행 중 외부 API를 호출하지 않으며, 설정에서 `일본어`, `한국어`, `함께 표시`를 선택할 수 있다.
- Yoiko 고유 역명 7,320개 전체를 자동 대조했고, 한국어 라벨이 하나로 확정된 6,738개만 asset에 넣었다. 나머지 582개는 데이터가 없거나 후보가 모호해 기존 일본어 원문을 유지한다.
- 생성기 `tool/generate_wikidata_station_korean_labels.mjs`는 Yoiko의 모든 고유 역명·노선을 Wikidata 후보와 대조하고, 중단 후 재개 가능한 로컬 캐시를 사용한다.
- 설정의 역명 표기 선택은 테마 선택과 동일한 전체 폭 3분할 UI로 통일했다. `일본어`·`한국어`에는 식별 아이콘을 두고 `함께 표시`에는 아이콘을 넣지 않았다.
- 기본 InkSparkle 효과는 일부 Android 기기에서 끊겨 보일 수 있어, 앱 전체 터치 효과를 가벼운 InkRipple로 조정했다. 테마·역명 표기 세그먼트 버튼은 여기에 220ms 전환을 적용한다.
- 악성 제보 대응으로 새 제보의 익명 Auth UUID를 서버 내부에서만 연결하고, 관리자 화면에서 UUID를 노출하지 않은 채 차단·해제할 수 있게 했다. 차단된 사용자의 요청은 저장 전 거절한다. `APPLIED`·`REJECTED` 문의와 검토 이력은 해결 후 1년이 지나면 매월 Cron으로 삭제하며, 진행 중 문의는 보존한다. 원격 migration·함수 배포와 실제 Cron 실행 확인은 대기 중이다.
- 문의 관리 상세에 제보 당시 앱 파서가 확인한 승차역·하차역 snapshot을 표시한다. 역명을 확인하지 못했거나 이전 payload에 값이 없으면 서버에서 재추측하지 않고 `null`로 명시한다.
- 오류 제보에 `역명 한글 표기 추가 요청`을 추가했다. 승차역·하차역·둘 다 중 범위를 선택한 뒤 각 파서 확인 역명을 기준으로 한글 표기를 제안하며, 한자 발음을 모르면 표기 없이 범위만 제보할 수 있다. 관리 화면에서 승차·하차 제안값을 따로 검토하고, 이전 앱 버전의 단일 한글 표기 제안도 누락 없이 표시한다. 역 코드·도시·노선 교정값을 추가로 요구하거나 추측하지 않는다.
- 문의 관리 상세는 제보 유형별로 관련된 제안값만 표시한다. 역 관련 제보에는 선택 범위와 해당 승차역·하차역의 파서 확인값 및 제안 역명·도시·노선을, 버스 회사 제보에는 제안 회사와 운행 도시·지역만 표시해 무관한 입력 없음 항목을 제거했다.
- Google Play 설치본은 앱 실행 뒤 홈 화면에서 백그라운드로 업데이트 가능 여부를 한 번 확인한다. 새 버전이 있을 때만 홈 안내 카드에서 업데이트를 시작할 수 있으며, 설정은 자동 확인 결과만 읽기 전용으로 표시한다. 업데이트 시작 중에는 홈 버튼을 비활성화해 반복 탭으로 Play 팝업이 겹치지 않게 한다. 네트워크 오류나 Play 밖에서 설치한 개발 빌드는 기존 NFC 기능을 막지 않고 업데이트 정보를 확인할 수 없음으로 처리한다.
- 교통패스 비교 Web 프로토타입 v0.3에서 Tokyo Metro 공식 지정 환승역 31개 조합을 ODPT 역 ID로 고정하고, Metro↔도에이 지하철 이동의 각 사업자 IC 운임 합계에서 70엔을 차감하는 연결 운임 계산을 추가했다. 계산된 구간은 Tokyo Subway Ticket 적용 대상으로 표시한다. 실제 노선·환승 시각을 탐색하지 않으므로 개찰 밖 환승의 60분 조건과 특수 운임은 대표 경로 대조 전까지 주의 문구로 남긴다.
- 교통패스 비교 Web 프로토타입은 시작 화면에서 `Tokyo Subway Ticket`, `도쿠나이 패스`, `오사카 주유패스 검증판`을 선택한 뒤 각각의 계산 화면으로 진입하도록 분리했다. Subway Ticket 화면은 24·48·72시간권만 전환할 수 있고, 도쿠나이 화면은 1일권만 고정 표시한다. 도쿠나이 패스에는 77개 적용 JR 역의 한국어·초성·일본어·영문 자동완성과 2,926개 무순서 역쌍 성인 IC 운임을 제공해 손익을 자동 계산한다. 운임표는 위키데이터 기반 거리와 2026년 JR 동일본 운임표를 바탕으로 계산·보정한 파생 데이터이므로, 화면에 참고용·구매 전 공식 안내 확인 문구를 표시한다. Tokyo Subway Ticket의 기존 ODPT 자동 역·성인 IC 운임 조회와 실제 개찰 하차역 입력 안내도 유지한다.
- 오사카 주유패스는 Web 검증판과 본 Android 앱의 패스 선택 화면에서 실행할 수 있다. 2026년 일반판 1일권 ¥3,500·2일권 ¥5,000, Osaka Metro·한큐·한신·게이한·긴테쓰·난카이의 적용 철도 183역과 동일 사업자 역쌍 6,394건, 철도 인접 간선 196개, 검토한 사업자 간 환승 연결 27개, 오사카 시티버스 일반 노선 정액 운임 ¥210을 경량 JSON으로 조회한다. 같은 사업자 이동은 직접 운임을 우선하고, 다른 사업자는 거리와 환승 부담을 반영한 경로를 찾아 회사별 승차 구간 운임을 합산한다. 일본어·한국어·초성 역 검색, 2일권 일차 지정, 일차별 버스 횟수와 손익 판정을 제공한다. 게이한 66개 역쌍은 Wikipedia 인접 영업거리 사실과 국토교통성 운임 자료로 재계산하고 생산 데이터에서 `keihan.co.jp`를 제외했다. 생성기는 전체 개수·간선 endpoint·환승 endpoint·중복·양수 운임·일반판 상품 가격·출처 조건을 검증한 뒤에만 asset을 쓴다. 추천 경로는 시간표 기반 최속 경로가 아니며 관광시설, 제외·온디맨드 버스, 특급권·좌석요금은 포함하지 않는다.
- 오사카 주유패스의 Android 계획 화면은 도쿠나이 패스·Tokyo Subway Ticket과 같은 `교통패스 비교` 헤더, 3단계 진행 막대, 선택 패스 요약 카드와 1·2일권 선택 UI, `이동 구간` 섹션으로 통일했다. 오사카에 필요한 출발·도착 역 선택 버튼, 이용일 선택, 버스 횟수, 환승 자동 운임·관광시설 제외 안내는 그대로 유지한다.
- 모든 패스의 이동 구간은 오사카 주유패스의 가운데 정렬형 출발·도착역 선택 필드와 같은 UI를 사용한다. 오사카 역 검색도 다른 패스처럼 `출발역 선택`·`도착역 선택` 제목 아래 상단 검색창, 검색 전·결과 없음 상태, 아이콘이 있는 결과 목록으로 통일했으며 `지원 철도 6개 사업자 전체` 안내 문구는 제거했다.
- 패스 입력 화면의 세부 배치도 통일했다. Tokyo Subway Ticket·도쿠나이 패스의 패스 요약은 오사카처럼 좌측 아이콘·이름·가격만 두고 `변경` 버튼을 제거했으며, 모든 역 선택 필드는 흰색 테두리·가운데 정렬 형태를 사용한다. 선택 전 `역 선택` 문구는 모든 패스에서 하늘색 강조색과 굵은 글꼴로 통일했다. 오사카는 역 선택 뒤 자동 운임 안내를 먼저 표시하고 이용일 칩을 그 아래에 배치해 Tokyo 방식과 맞췄다. 각 패스의 시간권·일권과 이용일 수는 변경하지 않았다.
- 역을 고른 뒤의 이동 구간 UI도 오사카 기준으로 통일했다. 세 패스 모두 선택한 역명을 하늘색 굵은 글꼴로, 바로 아래 운영사 정보와 함께 보여 주며 `성인 일반 운임 · ¥…` 형식의 안내를 사용한다. 역 선택 필드는 선택 전에는 60, 선택 후에는 76 높이로만 늘어나 운영사 정보를 담되 과도한 빈 공간은 만들지 않는다. 여러 이동 구간은 각자 별도 카드가 아니라 하나의 `이동 구간` 카드 안에 구분선과 함께 누적되고, 이용일 선택도 해당 출발·도착 필드와 운임 바로 아래에 붙는다.
- 이동 구간의 운영사명은 내부 식별자 대신 사용자용 한글 명칭으로 표시한다. `odpt.Operator:TokyoMetro`는 `도쿄메트로`, `odpt.Operator:Toei`는 `도에이 지하철`, `odpt.Operator:JR-East`는 `JR 동일본`으로 변환하며, 오사카 주유패스의 `Osaka Metro`도 `오사카 메트로`로 표기한다.
- Tokyo Subway Ticket·도쿠나이 패스의 약 10MB 운임 데이터는 패스 선택 화면에 들어오면 즉시 공유 캐시로 미리 읽는다. JSON 파싱과 검색 인덱스 생성은 별도 isolate에서 수행하고, 선택 시에는 준비된 데이터를 계획 화면에 직접 전달해 화면 전환 중 데이터 준비 상태가 갑자기 바뀌는 현상을 줄인다.
- 역 자동완성은 입력할 때마다 전체 비교 화면을 다시 그리지 않는다. 선택값과 운임은 즉시 비우되, 결과 패널 갱신은 마지막 입력 뒤 500ms 후에만 수행해 키보드 입력·추천 오버레이가 끊기거나 사라지는 현상을 줄였다.
- 도쿠나이 패스의 일반 운임 asset 생성기를 추가했다. 생성기는 도쿠나이 역 목록의 모든 무순서 역쌍에 대해 성인 IC 운임·JR 동일본 HTTPS 근거 URL·검증 일시가 있는지 확인하고, 하나라도 누락되면 asset을 쓰지 않는다. 완전 검증된 운임표에만 `tokunaiFareDataComplete`를 기록하므로 부분 데이터가 자동 손익 계산을 켜지 못한다.
- 사용자 제공 CSV를 app asset으로 바꾸는 `tool/import_tokunai_derived_fares.dart`를 추가했다. 일본어 역명을 내부 런타임 코드로 바꾸고 77개 역·2,926개 전량을 검증한 뒤에만 출력한다. 실제 asset에서 `小岩 → 葛西臨海公園` ¥440, `東中野` 자동완성 및 전량 운임 조회를 테스트했다.
- ODPT 원본에 한국어 표기가 없던 도에이 역 114개를 사용자가 `manual_odpt_station_names_ko.csv`에서 안정적인 ODPT 역 코드 단위로 보완했다. `tool/apply_odpt_korean_overrides.dart`는 기존 로컬 asset에 즉시 적용하고, `tool/import_odpt_pass_data.dart`도 이후 ODPT 전체 재가져오기 때 같은 CSV를 자동 병합한다. 141개 도에이 역의 한글명이 모두 채워졌으며, 미타·니시다이·신주쿠니시구치 표본과 코드 불일치·중복을 확인했다.
- 교통패스 비교를 본 Android 앱 홈의 `교통패스 비교` 카드로 연결했다. 앱 안에서 패스 선택 → 이용 계획 입력 → 별도 비교 결과 화면의 3단계 흐름으로 이동하며, Tokyo Subway Ticket은 24·48·72시간권만, 도쿠나이 패스는 1일권만 선택한다. 기존의 한국어·초성·일본어·영문 역 자동완성과 500ms 입력 디바운스는 그대로 유지했다. 지원 asset에서 운임을 확인한 구간만 손익에 합산하고, 확인하지 못한 운임은 추측하지 않는다. Metro↔도에이 연결은 지정 환승역·60분 이내 환승·70엔 할인 전제를 화면에 고지한다.
- 패스 선택 카드의 터치 구조를 하나의 잘린 Material·Ink 레이어로 통일하고 별도 Ink splash를 제거해, 테두리·아이콘·글자가 따로 움직여 보이던 현상을 없앴다. 홈의 `교통패스 비교` 진입 카드는 다크 모드에서 어두운 청록 배경, 흰 제목, 밝은 하늘색 아이콘·테두리를 사용해 배경과 글자가 섞이지 않도록 대비를 보완했다.
- 교통패스 비교의 확정된 입력 구조를 다크 모드에도 동일하게 적용했다. 패스 선택 카드·3단계 진행 막대·선택 패스 요약·기간/이용일 칩·이동 구간 카드·출발/도착 역 필드·역 교환 버튼·자동 운임 안내·구간 추가와 결과 버튼이 어두운 청록 표면, 밝은 하늘색 강조, 충분히 밝은 본문 글자라는 공통 대비 체계를 사용한다. 다크 모드의 기본 채움 버튼도 하늘색이 아니라 읽기 쉬운 진한 파랑 배경과 흰 글자로 고정했다.

## Android 출시 준비 순서

아래 순서는 사용자가 변경을 요청하기 전까지 출시 준비의 기본 순서로 사용한다.

1. **앱 기본 정보 확정**
   - 정식 앱 이름, 패키지 이름 유지 여부, 앱 버전과 빌드 번호를 정한다.
   - 앱 아이콘과 Play Store용 간단한 소개 문구를 준비한다.
2. **개인정보 및 권한 안내 작성**
   - 개인정보처리방침을 작성하고 NFC 사용 목적을 설명한다.
   - 오류 제보 시 Supabase로 전송되는 정보와 IDm·다른 이용내역·위치를 전송하지 않는다는 점을 명시한다.
   - Yoiko 역 코드 데이터의 출처와 이용 조건을 앱과 정책 문서에 표시한다.
3. **오류 제보 운영 보완**
   - 익명 로그인 악용 방지, 무료 DB 정기 백업, 오래된 익명 Auth 사용자 정리 방식을 정한다.
   - `RECEIVED`·`REVIEWING`·`VERIFIED`·`APPLIED`·`REJECTED` 상태의 운영 절차를 정한다.
   - 네트워크 중단 시 실패 안내와 수동 다시 시도를 최종 확인한다.
4. **Android release 설정**
   - 출시용 서명 키를 만들고 Git 저장소 밖에서 안전하게 관리한다.
   - release 난독화·최적화 정책과 버전 정보를 확정한다.
   - 서명된 Android App Bundle(AAB)을 생성한다.
5. **Play Console 준비**
   - 앱을 등록하고 아이콘·스크린샷·설명·개인정보처리방침 주소를 입력한다.
   - 데이터 보안 설문, NFC 기능과 지원 기기 안내를 작성한다.
   - 내부 테스트 트랙에 AAB을 업로드한다.
6. **출시 전 최종 점검**
   - 화면 크기, 라이트·다크 모드, NFC 꺼짐·카드 모드·시간 초과를 확인한다.
   - 이용내역 없는 카드와 다수 기록 카드, 오류 제보 성공·실패를 확인한다.
   - release 빌드에서 IDm과 원시 기록이 로그에 남지 않는지 확인한다.

- 전용 검색 화면 도입에 맞춰 이동 구간 카드를 다시 압축했다. 모바일에서도 `출발`과 `도착` 선택 필드를 한 줄에 배치하고 선택 전 문구를 `역 선택`으로 줄였으며, 검색 아이콘 대신 가운데 방향 전환 버튼으로 두 역을 실제 교환하고 운임을 다시 계산한다. 카드 안쪽 여백과 운임 요약·이용일 칩 간격도 줄였고 390px 너비에서 구간 추가·결과 진입과 역 교환을 회귀 테스트했다.
- 역 검색 입력 지연의 원인이던 키 입력별 전체 운임표 순회를 제거했다. `PassTransitData` 생성 시 335개 역의 정규화 한국어·일본어·영어·별칭과 초성을 검색 인덱스로 만들고, 49,372개 운임은 한 번만 순회해 Tokyo Subway Ticket·도쿠나이 패스별 사용 가능 역 ID 집합으로 변환한다. 이후 입력 중에는 인덱스 문자열과 ID 집합만 조회하며, 실제 병합 asset에서 패스별 역 제외와 초성 반복 검색을 회귀 테스트했다.

## 주요 기술 결정

- Phase 1에서는 원시 블록만 다루고 미확인 거래를 분류하지 않는다.
- IDm은 Android 명령 조립/응답 확인과 iOS 세션 내부에서만 일시 사용한다.
- Android `android.hardware.nfc`는 optional로 두고 런타임 가용성을 확인한다.
- 역 데이터 v1은 Yoiko 허가 조건 고지와 함께 번들 CSV를 한 번 로드해 메모리 인덱스로 사용한다. 데이터 단독 재배포는 금지하며 로컬 이용내역 SQLite 작업에서 사전 생성 DB 전환을 재검토한다.
- 정확 지역 조회 실패 후 단일 후보만 자동 확정하며 다중 후보는 유지한다.
- 신고는 사용자 미리보기·동의 후 한 건만 선택적으로 전송하고 자동 DB 반영하지 않는다.
- Phase 3는 디렉터리 확장 지점만 두며 Phase 2 완료 전 구현하지 않는다.
