# 프로젝트 에이전트 작업 규칙

이 문서는 `ic_card_reader` 프로젝트에서 AI 에이전트가 세션이 바뀌어도 계속 따라야 하는 영구 작업 규칙을 기록한다.

## 규칙 관리

- 작업을 시작하기 전에 이 문서를 확인한다.
- 사용자가 새로운 영구 작업 규칙을 정하거나 기존 규칙을 변경하면 같은 작업에서 이 문서를 갱신한다.
- 일회성 요청, 특정 화면의 단발성 수정 지시, 이미 완료된 작업 내용은 영구 규칙으로 기록하지 않는다.
- 새 규칙이 기존 규칙과 충돌하면 사용자의 최신 지시를 우선하고 이 문서도 최신 내용으로 정리한다.
- 제품 개발 진행 상황은 `docs/DEVELOPMENT_STATUS.md`에 기록하고, 에이전트 행동 규칙은 이 문서에 기록한다.

## 작업 및 검증

- 코드나 설정 파일을 조금이라도 수정하면 관련 테스트와 `flutter analyze`를 실행한다.
- 안전하게 실행할 수 있다면 전체 `flutter test`도 실행하여 기존 기능의 회귀 여부를 확인한다.
- 수정한 Dart 파일에는 포맷을 적용한다.
- 에이전트가 실행한 명령·개발 서버·감시 프로세스와 그 명령을 실행한 `cmd`/PowerShell 터미널 세션은 작업 뒤 반드시 종료한다. 포맷·분석·테스트를 포함한 각 명령 묶음이 끝난 직후 `cmd.exe`·PowerShell·Dart·Flutter 잔여 프로세스와 시작 시각을 확인하고, 에이전트가 시작한 것만 즉시 종료한다. 사용자가 명시적으로 유지해 달라고 요청한 프로세스만 예외로 한다.
- 사용자가 직접 빌드하므로 에이전트는 `flutter build`를 실행하지 않는다. 필요한 빌드 명령과 절차만 안내한다.
- 빌드 번호는 사용자가 직접 변경한다. 에이전트는 `pubspec.yaml`의 `version`을 변경하지 않고 변경 방법만 안내한다.
- 검증 결과를 최종 응답에 간단히 명시한다.
- 사용자에게 검증 결과를 안내할 때 앱 동작 오류와 자동검증의 기대값 불일치·대기 문제를 구분한다. 실제 앱 오류로 확인되지 않은 항목을 포괄적으로 `테스트 실패 N건`이라고 안내하지 않고 `자동검증 확인 필요 항목 N건`으로 표현하며, 확인된 원인과 미확정 사항을 설명한다. 명령의 실제 결과와 미통과 항목은 검증 기록에 정확히 유지하고, 전체 검증이 통과한 것으로 표현하지 않는다.

## 개발 우선순위와 범위

- Android를 우선 개발한다. iOS NFC 개발과 실기기 검증은 사용자가 다시 요청할 때까지 보류한다.
- 프론트엔드 UI/UX를 새로 만들거나 기존 화면의 시각 디자인을 변경하는 작업에서는 설치된 `frontend-design` 스킬을 기본으로 사용한다. 이 규칙의 범위는 레이아웃·여백·타이포그래피·색·아이콘·모션 등 디자인에 한정하며, 사용자의 명시적 요청 없이 기능 로직·데이터 처리·내비게이션 동작·기존 행동을 변경하지 않는다.
- Android 패키지 이름 `app.iccardreader.ic_card_reader`를 유지한다.
- 이용내역은 영구 로컬 저장하지 않고 현재 스캔 세션에서만 사용한다.
- 앱의 기본 디자인은 현재 하늘색 계열을 유지한다.
- 새 교통패스 기능은 기존 `교통패스 비교`의 확정 UI를 기본값으로 사용한다. 즉 패스 선택 카드, 3단계 진행 표시, 패스 설정 요약·기간 선택, 하나의 카드 안에 누적되는 이동 구간, 가운데 정렬형 출발·도착 역 필드, 역명·운영사·일반 운임 안내, 구간 추가·결과 버튼, 전용 역 검색 화면의 구조·여백·강조색을 임의로 다른 양식으로 만들지 않는다. 패스별로 필수인 입력만 추가하고, 새 UI가 필요하면 기존 구성 요소를 우선 확장한다. 라이트·다크 모드 모두에서 같은 계층과 충분한 명도 대비를 유지한다.
- 유효기간이 2일 이상인 패스도 손익 계산은 입력한 모든 이동의 일반 운임 합계를 패스 가격과 비교한다. 따라서 구간별 `이용일`·`n일차` 선택 UI는 제공하지 않는다. 기간·시간권 종류를 고르는 패스 설정은 유지한다.
- 앞으로 새 교통패스를 추가할 때도 기존 패스의 화면 구성 요소와 상호작용을 최대한 재사용해 통일성을 유지한다. 특히 제목·설명·역 선택 필드·운임 안내·버튼 등 대응 요소의 글자 크기와 두께를 기존 UI와 동일하게 맞춘다. 패스별 필수 기능 차이만 추가하며, 별도 양식·색 체계·검색 흐름을 새로 만들지 않는다.
- 교통패스 선택의 지역 목록은 등록된 패스 수를 기준으로 지원 지역을 먼저, 미구현 지역을 뒤에 자동 정렬한다. 같은 그룹 안에서는 `PassRegion`에 선언한 전국 기본 순서를 유지한다. 새 패스를 추가할 때는 `pass_selection_page.dart`의 `_PassListEntry`에 해당 지역을 반드시 지정해 지역별 패스 수·지원 상태·목록 노출이 함께 갱신되도록 한다.
- Notion의 `일본 교통패스 시장 조사와 구현 우선순위` 문서에서 `다음 구현 추천`은 항상 5개 후보를 순위·이유·난이도와 함께 유지한다. 후보를 구현 완료로 옮기면 해당 항목을 제거하고, 공식 판매·적용 범위·운임 자료를 다시 확인한 뒤 다음 후보를 보충해 5개를 유지한다. 이미 구현된 패스와 적용 구간 또는 운임 데이터가 크게 겹치는 후보는 추천에서 제외하며, 공통 UI를 재사용하는 점만으로는 중복으로 판단하지 않는다. 패스에 포함된 모든 교통수단이 전 구간 단일 균일요금이라 역간 운임 비교의 의미가 없는 상품도 추천 목록에서 제외한다. 관광시설 입장·쿠폰·상품·증정품 등 교통 외 혜택이 패스 가치에 실질적으로 포함되어 일반 운임만으로 정확한 손익을 판단하기 어려운 관광패스도 추천 목록에서 제외한다.
- 후쿠오카 지하철 1일권의 패스 요약·이동 구간·운임 안내·결과·도움말을 포함한 모든 화면에는 `공항선`·`하코자키선`·`나나쿠마선`을 별도 칩·목록·보조 정보·나열 문구로 표시하지 않는다. 적용 범위가 필요한 경우에도 이 세 노선명을 화면에 반복 노출하지 않고, 일반적인 `후쿠오카시 지하철` 표현을 사용한다.
- 후쿠오카 지하철 1일권 요약 카드의 가격은 다른 패스의 가격 표기와 같은 일반 굵기를 사용한다. 가격만 별도로 굵게 강조하지 않는다.
- 앞으로 새 교통패스의 요약 카드에서도 단일 상품 가격은 기존 패스와 같은 글자 크기·일반 굵기를 사용한다. 가격을 패스명보다 굵거나 큰 별도 강조 요소로 만들지 않는다.
- 기간·시간권처럼 둘 이상의 패스 종류를 고르는 버튼은 오사카 주유패스의 기간 선택 UI를 기준값으로 사용한다. 즉 2열 이상 동일 폭, 선택/미선택 하늘색 계열, 11 반경, 세로 9 여백, 기간 12pt·가격 11pt의 두 줄 구성과 7px 사이 간격을 유지한다.
- 새 화면의 일반 제목은 `FontWeight.w700`을 기본으로 사용한다. 결과 상태나 핵심 행동처럼 특별한 강조가 필요한 경우에만 더 굵은 두께를 사용한다.
- 역 선택 자동완성은 역명과 해당 역의 표기별칭만 후보로 사용한다. 모든 역에 공통인 사업자명·노선명은 후보에 넣지 않으며, 이 정보는 선택 결과의 보조 정보로만 표시한다. 초성 매칭은 `ㄱ`, `ㅅㅂ`처럼 한글 자모만으로 된 입력일 때만 적용하고, 완성형 한글 입력에는 역명 문자열 매칭만 적용한다. 짧은 입력이 공통 문자열이나 초성 때문에 무관한 전 역을 반환하지 않는 회귀 테스트를 새 패스마다 추가한다.
- 교통패스 역 선택·입력·결과에서 한국어 역명은 끝의 `역` 접미사 없이 표시한다. 원본 또는 매핑 데이터에 접미사가 있어도 표시 계층에서 중복 표기를 방지한다.
- 이동 구간의 출발·도착 선택 필드는 Tokyo Subway Ticket·도쿠나이 패스의 선택 완료 상태를 변경 불가 기준 레이아웃으로 사용한다. 모든 기존·신규 패스는 `presentation/widgets/pass_station_picker_field.dart`의 `PassStationPickerField`를 직접 사용하며, 별도 `OutlinedButton`·`Container` 조합으로 재구현하지 않는다. 선택 전 60dp·선택 후 76dp 높이, 가로 8dp 패딩과 세로 중앙 정렬, `출발/도착` 12sp·w600·보조색, 역명 14sp·w700·강조색, 운영사 보조 정보 `labelSmall` 및 한 줄 말줄임을 그대로 적용한다. 라벨→역명과 역명→보조정보의 간격은 각각 2dp로 고정한다. 구현·실기기 대조 절차는 `docs/agent/PASS_STATION_PICKER_GUIDE.md`를 따른다.
- 이동 구간의 자동 운임 안내는 모든 패스에서 색으로 채운 초록 배너를 사용하지 않는다. 흰 카드 배경 위에 체크 아이콘과 `성인 일반 운임 ¥금액`만 짧게 표시한다. 패스 적용 여부·프리구간·사업자·노선 등 부가 설명은 이 행에 덧붙이지 않는다.
- 이동 구간이 2개 이상이 되어도 첫 구간의 카드 상단 여백은 1개일 때와 동일해야 한다. 다중 구간에서만 표시하는 삭제 버튼은 기본 48dp `IconButton`을 직접 사용하지 않고 `presentation/widgets/pass_segment_remove_button.dart`의 `PassSegmentRemoveButton`을 사용해, 28dp 구간 번호 행의 높이를 늘리지 않는다.
- 모든 교통패스 데이터 저장소는 화면 재진입 때 asset을 다시 읽거나 파싱하지 않도록 저장소 단위의 공유 `Future` 캐시를 제공한다. `PassComparisonDataPreloader`에 등록하되, 교통패스 비교 진입 즉시 모든 지역을 병렬 사전 로딩하지 않는다. 사용자가 지역을 선택한 뒤 해당 지역 데이터만 먼저 준비하고, 지역 목록이 표시된 뒤 나머지 지역은 순차적으로 준비한다. 각 패스 화면은 같은 캐시 결과를 기다린다. 대용량·고정 운임표는 CSV·JSON 원본을 검증·생성용으로만 보관하고, 앱에는 인덱스 기반 binary asset을 배포한다. 대용량 문자열 파싱이 불가피하면 UI isolate에서 하지 않고 `compute` 등 백그라운드 작업을 사용한다.

## 개인정보와 데이터 처리

- 카드 IDm 원문을 로그, 로컬 저장소 또는 서버에 저장하거나 전송하지 않는다.
- 오류 제보에는 사용자가 선택한 이용내역 한 건과 필요한 익명 정보만 포함한다.
- 허가받은 Yoiko 역 코드 데이터는 애플리케이션과 함께 사용할 수 있지만 데이터만 별도로 재배포하지 않는다.
- 역 데이터의 출처와 허가 조건을 유지한다.

## 파싱 및 표시 원칙

- 실제 카드 fixture나 신뢰할 수 있는 근거로 검증되지 않은 거래 유형, 역, 사업자, 점포를 추측하지 않는다.
- 확인되지 않은 값은 `미확인`, `확인할 수 없음` 또는 이에 준하는 보수적인 문구로 표시한다.
- 실제 샘플이 없는 정산, 환불 및 기타 처리 코드는 임의로 분류하지 않는다.
- 원시 필드의 의미가 거래 유형마다 다르면 승차역 등의 기존 의미로 재사용하지 않고 별도 개념으로 모델링한다.

## 파일 및 Git 보호

- 사용자의 기존 변경사항과 관련 없는 파일을 수정하거나 되돌리지 않는다.
- 사용자가 만든 미추적 파일을 임의로 삭제하지 않는다.
- 특히 프로젝트 루트의 `ic_card_parsing_and_processing_complete.md`를 삭제하거나 덮어쓰지 않는다.
- 사용자가 명시적으로 요청하지 않는 한 커밋하거나 푸시하지 않는다.

## 문서화

- 일반 프로젝트 문서는 프로젝트 루트에 흩어놓지 않고 `docs/` 아래의 적절한 폴더에서 관리한다.
- 새 문서가 여러 주제로 늘어나면 `docs/agent`, `docs/release`, `docs/parsing`처럼 목적별 하위 폴더를 사용한다.
- 새 세션의 자동 규칙 발견에 필요한 루트 `AGENTS.md`와 프로젝트 진입점인 루트 `README.md`는 예외로 유지한다.
- 사용자 원본 문서는 명시적인 이동 요청 없이 임의로 위치를 변경하지 않는다.
- 작업을 시작할 때 `docs/planning/TODO.md`를 확인하고, 새로 확정된 작업이나 단계는 같은 문서에 추가한다.
- 작업이 진행 중이면 TODO 항목 앞에 `🚧`을 표시하고, 구현과 필수 검증이 모두 끝난 뒤에만 완료 처리한다.
- 완료된 항목은 결과를 `DEVELOPMENT_STATUS.md` 또는 해당 전문 문서에 옮긴 뒤 TODO에서 제거하여 TODO에는 미완료 작업만 남긴다.
- 각 개발 단계가 끝날 때 `docs/planning/TODO.md`에서 완료 항목과 다음 작업을 최신화하고 오래된 항목을 남겨두지 않는다.
- 기능 개발이나 중요한 수정이 완료되면 `docs/DEVELOPMENT_STATUS.md`에 진행 상황을 기록한다.
- 재현 가능한 미해결 문제나 제한사항이 생기거나 해결되면 `docs/KNOWN_ISSUES.md`의 상태도 함께 갱신한다.
- 테스트 범위나 결과가 달라지면 `docs/TEST_MATRIX.md`를 갱신한다.
- 파서 규칙처럼 별도 구현 문서가 있는 기능은 해당 문서의 구현 상태와 버전도 함께 갱신한다.
- 새로운 영구 에이전트 규칙이 추가될 때마다 이 `docs/agent/RULES.md`를 갱신한다.
