# 교통패스 손익 비교 기능 분석

- 최초 작성: 2026-08-12 (Asia/Seoul)
- 상태: ODPT 정적 데이터 가져오기·한국어 역 검색·Metro↔도에이 연결 운임 v0.3 구현
- 대상 1차 패스: Tokyo Subway Ticket 24/48/72시간권, 도쿠나이 패스

## 목표

사용자가 날짜·시각과 출발역·도착역으로 여러 이동을 입력하고 실제 이용할 경로를 선택하면, 선택한 교통패스의 적용 구간과 적용되지 않는 구간을 나누어 일반 운임 대비 손익을 계산한다.

결과에는 다음 값을 분리해 표시한다.

- 패스 미사용 총운임
- 패스 적용 가능 구간의 일반 운임
- 패스 적용 불가 구간의 추가 운임
- 패스 가격
- 패스 사용 시 총비용
- 절약액 또는 추가 지출액
- 계산하지 못한 구간과 사유

## Android 통합 v0.4

순수 Dart 계산 엔진과 정적 asset을 본 Android 앱에 연결했다. 홈의 `교통패스 비교` 카드에서 패스를 선택하고, 이동 구간을 입력한 뒤 별도 결과 화면에서 손익과 구간별 근거를 확인한다. 검증용 Flutter Web 진입점은 유지한다.

```powershell
flutter run -d chrome -t lib/pass_comparison_prototype.dart
```

현재 지원 범위:

- Tokyo Subway Ticket 24/48/72시간권 선택
- 사용 시작 날짜·시각과 여러 이동 구간 입력
- Tokyo Metro·도에이·패스 적용 외 구간 구분
- ODPT Tokyo Metro·도에이 역·노선·성인 IC 운임의 개발 시 정적 가져오기
- 한국어 역명 음절과 초성 검색 (`시`, `ㅅ`, `ㅅㅂㅇ` → `시부야`)
- 일본어·영어 역명 검색과 실제 ODPT 운임 자동 입력
- 공식 지정 환승역을 통한 Tokyo Metro↔도에이 지하철 연결 운임 자동 계산
- 유효시간 내 적용 구간만 합산
- 외부 구간 운임 비교 제외
- 이득·본전·손해·입력 부족 판정과 구간별 근거 표시
- 넓은 브라우저와 좁은 화면의 반응형 배치
- Android 앱의 패스 선택 → 이용 계획 → 비교 결과 3단계 흐름
- Android 역 선택 필드(라벨·안내 문구 분리) → 선택 대상 제목 아래 독립 검색창이 자동 포커스되는 전용 전체 화면 검색 → 결과 선택 후 원래 구간 복귀
- 이동 구간은 모바일에서도 출발·도착 선택을 한 줄에 표시하며, 가운데 방향 전환 버튼은 두 역과 운임 판정을 함께 갱신한다.
- 역 검색은 데이터 로드 시 패스별 사용 가능 역 ID와 정규화 이름·초성 후보를 미리 인덱싱한다. 키 입력 중에는 전체 운임표를 순회하거나 후보 문자열을 다시 정규화하지 않는다.

ODPT 액세스 토큰은 웹 번들에 포함하지 않는다. `tool/import_odpt_pass_data.dart`가 개발 환경의 `ODPT_ACCESS_TOKEN`으로 정적 JSON을 생성하며 앱은 생성물만 읽는다. 현재 저장소에는 토큰과 생성 JSON이 없으므로 실제 데이터 가져오기 실행은 토큰 설정 후 완료한다.

```powershell
$env:ODPT_ACCESS_TOKEN='발급된 토큰'
dart run tool/import_odpt_pass_data.dart
flutter run -d chrome -t lib/pass_comparison_prototype.dart
```

가져오기는 Station 응답뿐 아니라 Railway의 다국어 `stationTitle.ko`도 병합한다. 따라서 한국어 표기가 있는 역은 별도 번역 API 없이 한국어와 초성으로 검색된다. 같은 사업자 안에서는 ODPT `RailwayFare`의 정확한 역 ID 쌍만 사용한다. Metro↔도에이는 ODPT 원본에 직통 운임 행이 없으므로, Tokyo Metro 공식 IC 환승 목록의 지정 환승역을 역 ID로 고정하고 Metro/도에이 각각의 최저 IC 운임 합계에서 70엔을 차감해 계산한다. 이 계산은 지정 환승역에서 60분 이내 환승한다는 전제의 연결 운임 후보이며, 출발역·도착역만으로 실제 노선 경로까지 확정하지는 않는다.

출발·도착 입력에는 반드시 **실제로 개찰을 통과해 하차할 역**을 입력하도록 안내한다. 예를 들어 `西台 → 日比谷`에서 하차한 뒤 개찰 밖으로 걸어 有楽町 지역에 가는 경우 도착역은 `日比谷`이며, `有楽町`를 입력하면 유라쿠초선 개찰에 다시 들어가는 공식 개찰외 환승으로 해석된다. 역명만으로는 두 의도를 자동 구분할 수 없으므로, 자동 경로 후보를 구현하기 전에는 이 안내를 필수 UI 문구로 제공한다.

## 중요한 전제

출발역과 도착역만으로는 실제 이용 노선이 하나로 정해지지 않는다. 같은 역 사이에도 JR, Tokyo Metro, 도에이, 사철을 이용하는 여러 경로가 있고 경로에 따라 패스 적용 여부가 달라진다. 따라서 앱은 경로 후보를 제시하고 사용자가 실제 이용할 후보를 선택하도록 해야 한다.

패스 손익은 다음 식으로 계산한다.

```text
패스 미사용 비용 = 선택한 모든 경로의 일반 운임 합계
패스 사용 비용 = 패스 가격 + 패스 적용 불가 구간 운임 합계
절약액 = 패스 미사용 비용 - 패스 사용 비용
```

패스 적용 불가 구간이 있더라도 계산에서 이동 전체를 제외하지 않고 추가 운임으로 분리한다. 다만 정확한 운임 분할이 불가능한 경로는 임의 계산하지 않고 `계산 불가`로 표시한다.

패스 손익만 판단할 때는 패스 외부 운임이 사용 전후에 동일하므로 서로 상쇄된다. 따라서 ODPT 무료 MVP에서는 전체 외부 운임을 계산하지 않고 `패스 적용 구간의 일반 운임 합계 - 패스 가격`만 계산할 수 있다. 외부 노선이 섞인 이동은 사용자가 패스 진입역과 이탈역을 확인·선택하도록 하며, 외부 운임은 결과에 `비교 제외`로 표시한다.

## 현재 데이터로 바로 구현할 수 없는 이유

현재 Yoiko 역 코드 데이터는 NFC 기록의 지역·노선·역 코드를 역명으로 변환하기 위한 데이터다. 역 사이의 연결 순서, 환승 관계, 거리, IC/승차권 운임, 특례 운임과 개정 이력을 포함하지 않으므로 경로 탐색이나 운임 계산 데이터로 사용할 수 없다.

교통패스 기능의 역 검색 ID도 NFC 역 코드와 분리한다. NFC 화면은 Yoiko 코드를 계속 사용하고, 여행 계획 화면은 계약한 경로 API의 역 ID를 사용한다.

## ODPT 단독 구현 가능성 판단

### 결론

| 범위 | 가능성 | 판단 |
|---|---:|---|
| Tokyo Subway Ticket, 모든 이동이 Tokyo Metro·도에이 지하철 내부 | 높음 | 1차 MVP로 구현 가능 |
| Tokyo Subway Ticket, 사철·JR 직통 및 패스 외부 구간 포함 | 중간 이하 | 외부 사업자 데이터가 없으면 수동 추가 운임 필요 |
| 도쿠나이 패스 | 낮음 | JR 동일본 운임 데이터와 안정적인 상용 라이선스가 부족 |
| 두 패스를 포함한 범용 자동 경로·운임 계산 | 낮음 | ODPT만으로는 제품 수준 정확도를 보장하기 어려움 |

ODPT에는 Tokyo Metro와 도에이의 역·노선·시각표·운임 데이터가 있다. `odpt:RailwayFare`는 출발역·도착역별 승차권 운임과 IC 운임을 제공하므로 두 지하철 내부의 일반 운임 비교에 사용할 수 있다. 노선의 역 순서로 그래프를 만들고 환승역 매핑을 보완하면 자체 경로 후보도 만들 수 있다.

Tokyo Metro와 도에이를 한 번의 이동에서 연결하는 일반 운임은 각 사업자 운임 합계에서 성인 70엔을 할인하는 현재 공식 규칙을 구현했다. 적용 대상은 공식적으로 지정된 환승역이며, 개찰 밖 환승은 60분을 넘기면 운임이 분리된다. 현재 프로토타입은 입력 시각만 보유하고 실제 환승 시각·노선 순서를 탐색하지 않으므로 이 조건을 경고로 표시한다. 특수 구간과 직통 운전은 대표 경로 fixture 검증 전까지 보수적으로 확정하지 않는다.

반면 ODPT의 JR 동일본 자료는 현재 `공공교통 오픈데이터 챌린지 2026 한정`으로 표시되고, 관동 일부 노선만 제공한다. 카탈로그에서 JR 동일본의 역·노선·시각표는 확인되지만 `RailwayFare` 운임 데이터는 확인되지 않았다. 따라서 도쿠나이 패스의 각 JR 이동에 대한 일반 운임을 ODPT만으로 정확히 계산할 수 없다. 챌린지 한정 자료를 일반 Play Store 제품의 장기 기반 데이터로 사용하는 것도 라이선스 종료·특정 조건 위험이 있다.

### ODPT 기반으로 가능한 1차 제품

1. 패스를 Tokyo Subway Ticket 24/48/72시간권으로 제한한다.
2. 출발역과 도착역을 Tokyo Metro·도에이 지하철역으로 제한한다.
3. ODPT 정적 역·노선·운임을 개발 시 내려받아 버전이 있는 앱 데이터베이스로 변환한다.
4. 앱에서 정적 그래프 탐색과 운임 조회를 수행한다.
5. 지하철 밖 구간은 자동 계산하지 않고, 사용자가 패스 진입·이탈역을 선택하면 외부 운임을 손익 비교에서 제외한다. 전체 여행비까지 보고 싶을 때만 추가 운임을 수동 입력한다.
6. 도쿠나이 패스는 JR 운임 소스가 확보될 때까지 제공하지 않는다.

이 범위라면 런타임 경로 API 비용 없이 구현할 수 있다. 대신 데이터 갱신, 경로 탐색, 환승 규칙과 운임 회귀 검증을 개발자가 직접 유지해야 한다.

## 권장 데이터 방식

### 권장: 경로·운임 API + 자체 패스 적용 엔진

1. 경로 API에서 역 검색, 경로 후보, 노선·사업자·운임 구성요소를 받는다.
2. 앱의 패스 정의가 각 경로 구간을 적용 가능·불가로 판정한다.
3. 하나의 운임권이 패스 경계를 걸치는 경우 경계역에서 운임을 다시 분할 계산한다.
4. 선택한 모든 이동의 결과를 합산해 손익을 계산한다.

역스파아토 API는 역 후보, 경로, 노선 사업자, 운임과 운임 분할 기능을 제공하므로 1차 검토 대상으로 적합하다. 무료 플랜은 앱이 직접 계산에 사용할 완전한 경로 결과 대신 웹 결과 URL을 제공하므로 실제 제품 연동에는 평가판 또는 유료 계약 조건 확인이 필요하다.

NAVITIME API도 경로·운임 비교 기능을 제공하지만 공개된 소규모 유료 플랜의 비용이 더 높으므로 대안으로 비교한다.

공공교통 오픈데이터 센터(ODPT)는 무료 사용자 등록 후 사업자가 공개한 데이터를 API로 제공하고 상업·비상업 앱에 활용할 수 있다. 다만 데이터 제공 사업자와 개별 라이선스가 서로 다르고, 센터 자체가 완성된 환승 경로·운임 계산 엔진을 제공하는 것은 아니다. Tokyo Metro·도에이·JR 동일본의 필요한 정적 데이터와 운임이 모두 현재 카탈로그에 있는지 확인한 뒤, 패스 구간 목록의 보조 데이터나 장기적인 자체 엔진 후보로만 평가한다.

### 비권장: 앱에서 운임 전체를 자체 계산

Tokyo Metro, 도에이, JR의 노선 그래프와 거리·IC 운임표만 넣는 방식은 처음에는 저렴해 보이지만 최단 경로 운임, 특례 구간, 환승 할인, 직통 운전, 경계역, 운임 개정까지 직접 유지해야 한다. 1차 버전에는 적합하지 않다.

### 검증용 임시안: 사용자가 운임도 직접 입력

API 계약 전에는 출발역·도착역과 일반 운임을 사용자가 직접 입력하는 계산기부터 만들어 패스 합산 로직과 UI를 검증할 수 있다. 다만 최종 목표인 자동 운임 계산 기능은 아니다.

## 1차 패스 규칙

### Tokyo Subway Ticket

- 대상: Tokyo Metro 전 노선과 도에이 지하철 전 노선
- 종류: 첫 이용부터 24시간, 48시간, 72시간
- 2026-08 기준 성인 가격: 1,000엔, 1,500엔, 2,000엔
- 사철·JR 직통 구간은 해당 사업자 구간을 별도 운임으로 처리
- 상품별 구매 자격과 판매 조건을 결과 화면에서 별도로 안내

### 도쿠나이 패스

- 대상: 도쿄 23구 내 JR 동일본 보통열차·쾌속의 보통차 자유석
- 유효기간: 지정한 하루
- 2026-08 기준 성인 가격: 870엔
- 23구 밖으로 이어지는 이동은 패스 경계역을 기준으로 외부 구간 운임을 별도 계산

### 도쿠나이 패스 오프라인 운임 데이터 실현성 검토 (2026-08-23)

첨부된 오프라인 구축 가이드의 **사전 계산 후 로컬 조회** 방향은 실현 가능하다. 도쿄 대상 역 수가 제한적이므로 역 쌍별 최종 IC 운임을 생성해 두면, 앱은 출발·도착역 검색과 단순 조회만으로 빠르게 손익을 계산할 수 있다.

다만 다음 조건을 모두 충족해야 실제 제품에 넣을 수 있다.

1. 국토교통성 철도 공간 데이터나 역 데이터는 역·노선·연결 관계를 보완할 수 있지만, JR 운임 계산의 기준인 **인접 역별 영업킬로**를 대신하지 않는다. 좌표·선형 길이로 영업킬로를 추정하면 안 된다.
2. 2026-03-14 이후 JR동일본의 공식 운임표와 여객영업규칙을 규칙 데이터로 보관해야 한다. 거리 구간별 기본 운임 외에 특정 구간·경로·경계역의 특례를 별도 예외 테이블로 유지해야 한다.
3. 영업킬로의 신뢰 가능한 원천 및 그 원천을 앱 내 파생 운임표로 배포할 수 있는 이용 조건을 확보해야 한다. 출처가 불명확한 비공식 역간 거리만으로는 출시용 데이터 생성기를 만들지 않는다.
4. 도쿠나이 패스 적용 역·경계역을 공식 상품 조건에 따라 코드로 고정하고, 패스 밖으로 나가는 이동은 경계 기준 운임을 별도 검증해야 한다.
5. 생성한 운임은 JR 공식 운임 검색 결과와 대표 경로를 충분히 대조한다. 불일치는 최종 운임표를 수정하는 방식으로 처리하고, 추정값을 표시하지 않는다.

현재 Web 프로토타입에는 Flutter용 SQLite 플러그인을 그대로 쓸 수 없다. 생성 산출물은 작은 정적 JSON(또는 SQLite WASM)으로 조회하고, Android 앱 통합 단계에서만 SQLite를 선택하는 구성이 적합하다.

결론적으로, **정확한 영업킬로·특례의 합법적 원천을 확보하면 도쿠나이 패스의 오프라인 계산은 가능**하다. 반대로 현재 제안된 국토수치정보·역 데이터만으로는 정확한 JR 운임을 생성할 수 없으므로 바로 구현하면 안 된다.

### 구현된 2026년 파생 운임표 (2026-08-23)

사용자가 제공한 `fares_tokyo_wards_2026_corrected_full_graph.csv`를 도쿠나이 패스 Web 프로토타입의 오프라인 asset으로 변환했다. 표는 위키데이터 기반 역간 거리와 2026년 JR 동일본 거리 구간 운임표를 바탕으로 계산·보정된 결과이며, 다음 구조 검사를 통과했다.

- 적용 JR 역 77개와 모든 무순서 역쌍 `77C2 = 2,926`건이 포함된다.
- 중복 역쌍·자기 자신 역쌍·역 ID/역명 불일치가 없다.
- IC 운임은 ¥155~¥616이며, 입력 운임거리와 2026년 거리 구간 운임표의 금액이 일치한다.
- 기존 목록에서 누락됐던 `大久保`, `東中野`, `市ケ谷`를 추가했다.
- `小岩 → 葛西臨海公園`은 표의 최단 계산 경로가 구역 밖 역을 경유한다는 메모가 있으나, 두 끝 역 모두 적용 역이므로 일반 운임 ¥440과 도쿠나이 적용 역쌍으로 유지한다. 앱은 실제 탑승 경로를 추적하거나 판정하지 않는다.

생성 도구 `tool/import_tokunai_derived_fares.dart`는 CSV의 일본어 역명을 앱 내부 역 코드에 연결하고, 전량이 존재할 때만 asset을 쓴다. 파생 데이터는 빠른 참고용 손익 계산에 사용하며, 운임 개정 또는 예외 검토 때는 대표 역쌍을 JR 동일본 공식 결과와 다시 대조해야 한다.

가격과 규칙에는 `validFrom`, `validUntil`, `lastVerifiedAt`, 공식 출처 URL을 저장한다. 현재 날짜에 유효한 정의가 없으면 계산을 중단하고 업데이트가 필요하다고 안내한다.

## 권장 도메인 구조

```text
PassDefinition
  id, 이름, 가격, 유효 방식, 적용 규칙, 구매 조건, 출처, 적용 기간

PlannedJourney
  날짜·시각, 출발역, 도착역, 선택한 RouteCandidate

RouteCandidate
  총운임, 소요시간, TransitLeg 목록, FareComponent 목록

TransitLeg
  승하차역, 사업자, 노선, 열차 종류, 패스 적용 상태

PassEvaluation
  일반 총운임, 적용 구간 운임, 미적용 운임, 패스 가격,
  패스 사용 총비용, 절약액, 판정, 경고 목록
```

판정은 `beneficial`, `breakEven`, `notBeneficial`, `insufficientData` 네 가지로 둔다. 일부 구간의 운임을 신뢰할 수 없으면 숫자를 억지로 합산하지 않고 `insufficientData`로 처리한다.

## 권장 서버 구조

API 키는 Flutter 앱에 포함하지 않는다. 기존 Supabase Edge Function을 확장하거나 별도 함수 `transit-route-search`를 만들어 다음 흐름으로 처리한다.

```text
Flutter 앱
  -> Supabase Edge Function
  -> 계약한 경로·운임 API
  -> 정규화한 경로 후보 반환
  -> 앱 또는 함수에서 패스 적용 계산
```

- 경로 API 키는 Supabase secret에 저장한다.
- 익명 사용자별 요청 제한을 둔다.
- 사용자가 입력한 일정과 역은 기본적으로 DB에 저장하지 않는다.
- 서버 로그에는 전체 일정과 상세 경로가 남지 않도록 한다.
- 외부 전송이 추가되므로 개인정보처리방침과 Play 데이터 보안 답변을 재검토한다.
- API 응답 캐시는 계약 약관이 허용하는 범위에서만 사용한다.

## UI 흐름 제안

1. 비교할 패스를 선택한다.
2. Tokyo Subway Ticket은 계획 화면에서 24·48·72시간권을 고른다. 첫 이용 예정 날짜·시각은 입력받지 않으며, 도쿠나이 패스도 사용일 없이 단일 1일권 계획으로 취급한다.
3. `이동 구간 추가`로 출발역·도착역을 여러 건 입력한다. Tokyo Subway Ticket은 선택한 권종 범위 안에서 각 구간에 `1일차~3일차`만 지정하며, 도쿠나이는 구간별 시간 입력을 받지 않는다.
4. 앱은 자동으로 확인한 적용 여부와 성인 IC 운임을 각 구간의 짧은 요약으로 표시한다. 실제 개찰을 통과한 하차역을 입력하도록 안내한다.
5. 결과 화면에서 `이득`, `동일`, `손해`, `계산 불가`와 구간별 근거를 표시한다.

결과 예시는 다음과 같다.

```text
일반 운임 합계          ¥1,420
패스 가격              ¥1,000
패스 미적용 추가 운임    ¥180
패스 사용 시 합계       ¥1,180
예상 절약액              ¥240
```

## 구현 단계

1. **완료:** 수동 운임 기반 순수 Dart 손익 계산 엔진과 별도 웹 입력·결과 UI를 만든다.
2. ODPT 실제 JSON으로 역·노선·운임·라이선스 조건을 검증한다.
3. **완료:** Tokyo Metro·도에이 공식 환승역 매핑과 70엔 연결 할인을 정적 운임 조회에 적용한다.
4. 자동 경로 후보와 운임을 수동 입력 대신 연결한다.
5. 공식 경로 검색 결과와 최소 20개 대표 이동을 대조한다.
6. 필요한 경우에만 Supabase 프록시와 요청 제한·비저장 정책을 구현한다.
7. 본 앱에 통합하기 전에 개인정보처리방침·데이터 보안·출처·면책 문구를 갱신한다.

## 오사카 주유패스 Web 검증판 (2026-08-24)

Web 전용 진입점과 본 Android 앱에서 같은 입력 흐름과 교통비 손익 계산을
검증한다. 2026년 공식 안내 기준 일반 1일권은 ¥3,500,
2일권은 ¥5,000이며, 1일 이용 시간은 오전 3시부터 다음 날 오전 2시 59분
까지다. 교통수단은 각 사업자의 첫차부터 막차까지 이용한다.

현재 범위는 다음과 같다.

- 검증된 2026년 데이터에서 Osaka Metro와 한큐·한신·게이한·긴테쓰·난카이의
  주유패스 적용 철도 183역과 동일 사업자 역쌍 6,394건을 경량 JSON으로
  생성한다.
- 기존 코드 단위 한국어 표기를 병합하고 일본어·한국어·초성 검색을 제공한다.
- 1일권과 2일권을 선택하고, 2일권은 각 구간에 1일차·2일차를 지정한다.
- 철도 출발·도착역을 선택하면 같은 사업자는 성인 일반 편도 운임을 바로
  조회한다. 사업자가 바뀌면 인접 철도 간선 196개와 검토한 환승 연결 27개의
  정적 그래프에서 거리·환승 부담 기반 경로를 찾고, 회사별 승차 구간으로
  나눈 운임을 자동 합산한다.
- 주유패스 대상 오사카 시티버스 일반 노선은 일차별 탑승 횟수와 성인 정액
  운임 ¥210을 합산한다. 일부 특정 노선과 온디맨드 버스는 대상에서 제외한다.
- 자동 교통비 합계와 패스 가격 차이로 `이득`, `동일`, `손해`, `입력 부족`을
  판정한다.
- 관광시설 무료입장 가치, 특급권·좌석요금과 제외 버스는 계산하지 않는다.
- 추천 경로는 시간표·실시간 운행정보를 사용한 최속 경로가 아니므로 실제
  이용 경로와 다를 수 있음을 계획·결과 화면에 표시한다.

통합 asset은 공식 역쌍 검색 결과를 복제하지 않는다. Osaka Metro는 인접역
영업거리와 공개 운임 규칙, 사철은 각 공개 운임 자료와 계산 규칙으로 만든
파생 운임을 사용한다. 게이한 66개 역쌍은 Wikipedia의 인접 영업거리 사실과
국토교통성 운임 자료로 재계산하며, 생산 데이터에 `keihan.co.jp`를 사용하지
않는다. 생성기는 183역·6,394쌍·196개 철도 간선·27개 환승 연결, endpoint
누락·중복·양수 운임과 해당 출처 조건을 검사한 뒤에만 asset을 쓴다. Web과
Android 코드 경로는 같은 asset과 계산기를 사용하며, 실기기 대표 환승 구간
검증과 최신 공식 조건 재확인은 계속 필요하다.
