# 교통계 IC 이용이력 파서 1차 수정안

> 구현 상태: 2026-08-12 완료. `phase2-parser-v2`에 반영했으며, 문서의 "현재 구현" 설명은 수정 전 상태를 기록한 것이다. 추가 요구에 따라 `08/02`의 처리 장소 코드를 별도 거래 장소로 모델링하고 자동발권기 충전역을 목록·상세 화면에 표시한다.

## 1. 문서 목적

이 문서는 다른 개발 세션에서 바로 구현할 수 있도록, 실제 카드에서 확인된 `090F` 16바이트 이용이력과 공개된 Suica/FeliCa 역분석 자료를 바탕으로 1차 수정 범위를 정리한다.

핵심 목표는 다음 네 가지다.

1. 일반 개찰기 `16/01`만 철도로 인식하는 현재 규칙을 다른 개찰 단말까지 안전하게 확장한다.
2. 자동발권기 충전 `08/02`를 충전으로 인식한다.
3. 매장 계열 충전 `C8/49`의 사용자 표시를 과도하게 구체화하지 않는다.
4. 마지막 바이트의 지역 코드를 상위 2비트로 정규화한다.

이 문서는 구현 지시서이자 1차 개선 기록이며, 공개되지 않은 사양을 확정 규격처럼 취급하지 않는다. 실제 샘플로 확인된 규칙과 공개 역분석 자료만으로 확인된 후보를 아래에서 구분한다.

## 2. 현재 구현의 문제

현재 분류기는 `lib/src/features/transaction_history/data/transit_history_parser.dart`에서 다음 조합만 철도로 인정한다.

```dart
if (terminal == 0x16 && process == 0x01) {
  return TransitTransactionType.rail;
}
```

그 결과 연락·환승 개찰기에서 생성된 실제 철도 기록 `1D/01`이 `unknown`으로 떨어진다. 역 조회는 `rail` 기록에만 수행되므로, 역 DB에 코드가 존재해도 역명 조회까지 건너뛴다.

충전도 현재 `C8/49`와 잔액 증가가 동시에 확인될 때만 인식한다. 따라서 역 자동발권기에서 충전한 `08/02`는 `unknown`으로 표시된다.

또한 현재 파서는 다음처럼 마지막 바이트 전체를 지역 코드로 저장한다.

```dart
regionCode: bytes[15],
```

실제 기록에서는 지역 값이 마지막 바이트의 상위 2비트에 있으므로 `C0`은 지역 `03`으로 해석해야 한다.

## 3. 확인된 16바이트 기본 배치

철도·발권기 계열 기록에 적용할 기본 배치는 다음과 같다.

| 바이트 | 길이 | 의미 |
|---|---:|---|
| 0 | 1 | 단말 코드 |
| 1 | 1 | 처리 코드 |
| 2~3 | 2 | 처리 세부 정보; 이번 수정에서 추정하지 않음 |
| 4~5 | 2 | 날짜 |
| 6 | 1 | 승차 노선 코드 또는 처리 장소 노선 코드 |
| 7 | 1 | 승차역 코드 또는 처리 장소 역 코드 |
| 8 | 1 | 하차 노선 코드 |
| 9 | 1 | 하차역 코드 |
| 10~11 | 2 | 처리 후 잔액, little-endian |
| 12~14 | 3 | 거래 순번 |
| 15 상위 2비트 | 2bit | 지역 코드 |

지역 코드는 다음처럼 추출한다.

```dart
final regionCode = (bytes[15] >> 6) & 0x03;
```

원본 마지막 바이트는 `RawHistoryBlock`에 이미 보존되므로 별도 필드를 추가하지 않아도 된다.

## 4. 단말 코드 조사 결과

### 4.1 개찰 관련 단말

| 단말 코드 | 공개 자료의 의미 | 1차 수정 판단 | 근거 수준 |
|---|---|---|---|
| `0x16` | 일반 개찰기(改札機) | `01`과 조합 시 철도 | 기존 실제 fixture 확인 |
| `0x17` | 간이 개찰기(簡易改札機) | `01`과 조합 시 철도 | 복수 공개 파서 일치; 로컬 실제 fixture 없음 |
| `0x1A` | 개찰 단말(改札端末) | `01`과 조합 시 철도 | 복수 공개 파서 일치; 로컬 실제 fixture 없음 |
| `0x1D` | 연락·환승 개찰기(連絡改札機) | `01`과 조합 시 철도 | 사용자 제공 실제 기록 확인 |
| `0x23` | 신칸센 개찰기(新幹線改札機) | 1차 수정 보류 | 공개 파서에는 있으나 로컬 실제 fixture 없음; 처리 코드 `13` 별도 의미 |

JR 동일본 공식 안내에서도 일반 자동개찰기, 간이 Suica 개찰기, 신칸센 환승 개찰기, 타사선 환승 개찰기가 서로 다른 설비로 존재함을 확인할 수 있다. 다만 `090F` 내부 단말 숫자 매핑은 공식 공개 사양이 아니라 복수 공개 구현의 역분석 결과다.

### 4.2 철도 관련이지만 단순 승하차로 분류하면 안 되는 단말

| 단말 코드 | 의미 | 주의사항 |
|---|---|---|
| `0x03` | 정산기 | 정산·입장 정산 등 처리 코드와 함께 판단해야 함 |
| `0x08` | 자동발권기 | `02`는 충전, `03`은 승차권 구매, `07`은 신규 발행/초기화 |
| `0x18`, `0x19` | 창구 단말 | 환불·정산·재발행 등 다양한 처리 가능 |
| `0x1C` | 환승 정산기 | 개찰 승하차가 아니라 정산 처리 가능 |
| `0x14`, `0x15` | 발권기 계열 | 단말 코드만으로 유형을 정하지 않음 |

단말 코드만 보고 모든 철도 시설 기록을 `rail`로 분류해서는 안 된다. 반드시 처리 코드와 필요한 경우 노선·역 코드 존재 여부를 함께 확인한다.

## 5. 처리 코드 조사 결과

이번 1차 수정에 직접 사용하는 처리 코드는 다음과 같다.

| 처리 코드 | 의미 | 비고 |
|---|---|---|
| `0x01` | 운임 지불/개찰 출장 | 개찰 관련 단말과 조합할 때 철도 승하차 |
| `0x02` | 충전 | `08/02` 자동발권기 충전 실제 기록 확인 |
| `0x03` | 자기 승차권 구매 | `08/03` 후보; 1차 수정에서 새 enum 추가는 보류 가능 |
| `0x07` | 신규 발행/초기화 | 현재처럼 `08/07`, `12/07`, `22/07` 숨김 유지 |
| `0x0D`, `0x0F` | 버스 계열 | 기존 검증 범위 유지 |
| `0x13` | 신칸센 이용 지불 | `23/13` 실제 fixture 확보 전 보류 |
| `0x46` | 물품 구매 | 기존 `C7/46`, `C8/46` 유지 |
| `0x49` | 레지 입금 | `C8/49` 매장 계열 충전 |

## 6. 실제 샘플 A: 연락·환승 개찰기 철도 이용

원본:

```text
1D01000232B9F109F104480A00002A00
```

분해:

```text
1D 01 00 02 | 32 B9 | F1 09 | F1 04 | 48 0A | 00 00 2A | 00
```

예상 결과:

| 항목 | 값 |
|---|---|
| 단말 | `0x1D`, 연락·환승 개찰기 |
| 처리 | `0x01`, 운임 지불 |
| 유형 | `TransitTransactionType.rail` |
| 날짜 | `2025-05-25` |
| 지역 | `0x00` |
| 승차 코드 | `00-F1-09` |
| 승차역 | 馬喰横山, 바쿠로요코야마 |
| 하차 코드 | `00-F1-04` |
| 하차역 | 市ヶ谷, 이치가야 |
| 노선 | 도에이 지하철 신주쿠선 |
| 처리 후 잔액 | `0x0A48 = 2,632엔` |
| 거래 순번 | `0x00002A = 42` |

앱의 역 DB에 두 역이 이미 존재한다.

```text
assets/data/stations/yoiko_station_codes.csv
00-F1-09 = 東京都交通局 / 10号線 新宿線 / 馬喰横山
00-F1-04 = 東京都交通局 / 10号線 新宿線 / 市ヶ谷
```

## 7. 실제 샘플 B: 자동발권기 충전

원본:

```text
0802000030F6E91F0000A60400000FC0
```

분해:

```text
08 02 00 00 | 30 F6 | E9 1F | 00 00 | A6 04 | 00 00 0F | C0
```

예상 결과:

| 항목 | 값 |
|---|---|
| 단말 | `0x08`, 자동발권기 |
| 처리 | `0x02`, 충전 |
| 유형 | `TransitTransactionType.charge` |
| 날짜 | `2024-07-22` |
| 원시 지역 바이트 | `0xC0` |
| 정규화 지역 | `(0xC0 >> 6) & 0x03 = 0x03` |
| 처리 장소 코드 | `03-E9-1F` |
| 처리 장소 | 福岡市交通局 / 3号線(七隈線) / 天神南 |
| 처리 후 잔액 | `0x04A6 = 1,190엔` |
| 거래 순번 | `0x00000F = 15` |

이 기록 하나만으로 충전액은 알 수 없다. 바로 다음의 더 오래된 기록이 있을 때만 다음처럼 계산한다.

```text
충전액 = 현재 기록의 처리 후 잔액 - 더 오래된 기록의 처리 후 잔액
```

이전 기록이 없거나 잔액 증가가 확인되지 않아도 `08/02`라는 유형 자체는 충전으로 유지하고, 금액만 계산 불가 또는 의심 상태로 둔다.

`E9-1F`는 이 충전 기록에서 승차역이 아니라 발권기 처리 장소 코드다. 구현에서는 승차역 필드를 UI에서 재사용하지 않고 별도 `transactionLocation` 코드로 보존하며, 역 DB에서 정확히 조회되는 경우 충전역과 노선명을 표시한다.

## 8. `C8/49`의 올바른 표현

`C8/49`는 충전으로 분류한다. 다만 `편의점 충전`으로 단정하지 않는다.

확정 가능한 범위:

- `0x49`: 레지 입금(レジ入金)
- `0xC8`: 판매·전자머니 계열 단말로 역분석됨
- 결론: 매장 또는 충전 지원 판매 단말에서 이루어진 충전

가능한 장소에는 편의점, 슈퍼마켓, 소매점 계산대, 역내 매장 등이 포함될 수 있다. `090F`만으로 정확한 상호를 확정하기 어렵다.

권장 사용자 문구:

```text
목록: 매장에서 충전
상세 유형: 충전
상세 방식: 매장 단말
상세 장소: 확인할 수 없음
```

피해야 할 문구:

```text
편의점 충전
```

기존 실제 fixture 예시:

```text
C849000034E378CAC0CE880800012600
```

현재 구현은 이 조합에서 이전 기록과 비교해 잔액이 증가한 경우에만 `charge`로 분류한다. 1차 수정에서는 단말·처리 조합으로 유형을 먼저 확정하고, 잔액 비교는 충전액 계산과 이상 여부 판정에만 사용한다.

## 9. 권장 분류 로직

### 9.1 철도 승하차

```dart
const conventionalRailGateTerminals = <int>{
  0x16, // 일반 개찰기
  0x17, // 간이 개찰기
  0x1A, // 개찰 단말
  0x1D, // 연락·환승 개찰기
};

final hasBoardingCode =
    current.boardingLineCode != 0 || current.boardingStationCode != 0;
final hasAlightingCode =
    current.alightingLineCode != 0 || current.alightingStationCode != 0;
final hasCompleteRailRoute = hasBoardingCode && hasAlightingCode;

if (process == 0x01 &&
    conventionalRailGateTerminals.contains(terminal) &&
    hasCompleteRailRoute) {
  return TransitTransactionType.rail;
}
```

`1D/01`은 실제 샘플로 확인됐다. `17/01`, `1A/01`은 공개 코드표의 의미와 처리 코드 조합상 1차 지원 대상으로 포함하되, 로컬 실제 fixture가 아직 없다는 사실을 테스트명과 문서에 남긴다.

### 9.2 충전

```dart
if (terminal == 0x08 && process == 0x02) {
  return TransitTransactionType.charge;
}

if (terminal == 0xC8 && process == 0x49) {
  return TransitTransactionType.charge;
}
```

유형 분류는 이전 기록 존재 여부나 잔액 증가에 의존하지 않는다. 이전 기록은 금액 계산에만 사용한다.

### 9.3 기존 규칙

다음 기존 규칙은 유지한다.

- `05/0D`: 버스
- `C7/46`, `C8/46`: 물품 구매
- `08/07`, `12/07`, `22/07`: 초기화 기록으로 숨김

### 9.4 분류 순서 권장

서로 다른 레이아웃을 오인하지 않도록 명시적인 조합부터 판정한다.

1. 초기화 기록 제외
2. 물품 구매
3. 버스
4. 충전 `08/02`, `C8/49`
5. 철도 개찰 `16|17|1A|1D` + `01` + 완전한 승하차 코드
6. 그 외 `unknown`

## 10. 금액 계산 규칙

유형과 금액 계산을 분리한다.

### 충전

- 이전 기록이 있고 현재 잔액이 더 크면 `balanceIncrease`와 충전액을 표시한다.
- 이전 기록이 없으면 유형은 `charge`, 금액은 `noOlderRecord`로 둔다.
- 이전 기록이 있지만 잔액이 증가하지 않으면 유형은 `charge`로 유지하고 금액 상태만 `suspicious` 또는 별도 사유로 둔다.

### 철도·버스·물품 구매

- 기존처럼 더 오래된 기록 잔액에서 현재 잔액을 빼서 사용액을 계산한다.
- 잔액이 줄지 않았으면 일반 이용 금액으로 표시하지 않는다.

## 11. UI 문구 수정안

충전의 목록·상세 보조 문구는 원시 단말/처리 코드로 구분할 수 있다. 새 enum을 만들지 않고도 `terminalCode`, `processCode`를 사용하는 presentation helper로 1차 구현 가능하다.

```dart
String chargeSummary(ParsedTransitHistory history) {
  if (history.terminalCode == 0x08 && history.processCode == 0x02) {
    return '자동발권기에서 충전';
  }
  if (history.terminalCode == 0xC8 && history.processCode == 0x49) {
    return '매장에서 충전';
  }
  return '카드 충전';
}
```

권장 표시:

| 조합 | 목록/요약 문구 |
|---|---|
| `08/02` | 자동발권기에서 충전 |
| `C8/49` | 매장에서 충전 |
| 기타 충전 | 카드 충전 |

`C8/49`에 `편의점`이라는 표현을 사용하지 않는다.

## 12. 필수 테스트

### 12.1 파서 회귀 테스트

1. `1D01000232B9F109F104480A00002A00`
   - `rail`
   - 날짜 `2025-05-25`
   - 지역 `0`
   - 승차 `F1-09`
   - 하차 `F1-04`
   - 잔액 `2632`

2. `0802000030F6E91F0000A60400000FC0`
   - `charge`
   - 날짜 `2024-07-22`
   - 지역 `3`
   - 처리 장소 코드 `E9-1F`
   - 잔액 `1190`
   - 단독 기록이면 유형은 충전, 금액만 `noOlderRecord`

3. 기존 `C849...` fixture
   - 이전 기록이 없어도 유형은 `charge`
   - 이전 기록이 있고 잔액 증가 시 충전액 계산

4. 합성 `17/01` 기록
   - 완전한 승하차 코드가 있으면 `rail`

5. 합성 `1A/01` 기록
   - 완전한 승하차 코드가 있으면 `rail`

6. `17/01` 또는 `1A/01`이지만 승차나 하차 코드 쌍이 비어 있는 기록

## 17. 후속 실제 샘플 분석: `17/01` 간이 개찰기

원본:

```text
1701000234DE44244428EC0400000300
```

분해:

```text
17 01 00 02 | 34 DE | 44 24 | 44 28 | EC 04 | 00 00 03 | 00
```

예상 결과:

| 항목 | 값 |
|---|---|
| 단말 | `0x17`, 간이 개찰기 |
| 처리 | `0x01`, 운임 지불/개찰 출장 |
| 유형 | `TransitTransactionType.rail` |
| 날짜 | `2026-06-30` |
| 지역 | `0x00` |
| 승차 코드 | `00-44-24` |
| 승차역 | 高山, 다카야마 |
| 하차 코드 | `00-44-28` |
| 하차역 | 飛騨古川, 히다후루카와 |
| 노선 | JR 도카이 高山線, 다카야마선 |
| 처리 후 잔액 | `0x04EC = 1,260엔` |
| 거래 순번 | `0x000003 = 3` |

이 기록은 단순히 `高山에서 무언가를 한 기록`이 아니다. 바이트 6~7은 승차역, 바이트 8~9는 하차역으로 해석되므로 **다카야마에서 승차해 히다후루카와에서 하차한 철도 이용**이다. `0x17`은 간이 개찰기이므로, 이 기록을 쓴 장치는 하차역 측 간이 개찰기였을 가능성이 높다.

이 한 건만으로 운임은 계산할 수 없다. 운임은 이 기록보다 바로 오래된 기록의 처리 후 잔액과 비교해야 한다.

이 샘플로 기존 문서에서 공개 코드표 근거만 있던 `17/01`을 실제 카드 샘플 확인 항목으로 승격한다. 다음 회귀 테스트를 추가한다.

```text
raw: 1701000234DE44244428EC0400000300
type: rail
date: 2026-06-30
region: 0
boarding: 44-24 / 高山
alighting: 44-28 / 飛騨古川
balance: 1260
```

## 18. 후속 실제 샘플 분석: `CA/46` 물품 결제

원본:

```text
CA46000034E35DA49B0AE60000000900
```

분해:

```text
CA 46 00 00 | 34 E3 | 5D A4 | 9B 0A | E6 00 | 00 00 09 | 00
```

물품 구매 계열에서는 철도와 달리 바이트 6~7이 시각으로 사용된다. `0x5DA4`를 시각 비트 필드로 풀면 다음과 같다.

```text
hour   = 0x5DA4 >> 11          = 11
minute = (0x5DA4 >> 5) & 0x3F = 45
second = (0x5DA4 & 0x1F) * 2  = 8
```

예상 결과:

| 항목 | 값 |
|---|---|
| 단말 | `0xCA`, 정확한 단말 명칭은 현재 미확인 |
| 처리 | `0x46`, 물품 구매/지불 |
| 유형 | `TransitTransactionType.purchase` |
| 일시 | `2026-07-03 11:45:08` |
| 점포·단말 코드 후보 | `9B-0A`; 정확한 상호 확인 불가 |
| 처리 후 잔액 | `0x00E6 = 230엔` |
| 거래 순번 | `0x000009 = 9` |
| 지역 | `0x00` |

다른 앱이 이 기록을 `支払`로 표시한 것은 의미상 타당하다. 한국어 사용자 문구는 기존 제품 용어에 맞춰 `물품 구매` 또는 `결제`로 표시할 수 있다. `CA`의 정확한 단말 이름이나 점포 업종은 이 기록만으로 단정하지 않는다.

두 제공 기록이 실제 카드 이력에서 서로 연속이고, `CA/46`이 더 최신 기록이라면 잔액 차이는 다음과 같다.

```text
1,260엔 - 230엔 = 1,030엔
```

이 조건에서 결제액은 `1,030엔`이다. 두 기록 사이의 다른 이력이 생략됐다면 금액을 확정할 수 없으므로, 원래 `090F` 배열에서의 인접 여부를 확인해야 한다.

### 18.1 현재 앱의 누락

현재 파서는 다음 두 단말만 `process == 0x46` 물품 구매로 인정한다.

```dart
if ((terminal == 0xC7 || terminal == 0xC8) && process == 0x46) {
  return TransitTransactionType.purchase;
}
```

따라서 실제 `CA/46` 샘플은 현재 `unknown`으로 떨어진다.

### 18.2 보수적인 수정안

실제 샘플이 확보된 `0xCA`만 물품 구매 단말 집합에 추가한다.

```dart
static const _purchaseTerminals = <int>{
  0xC7,
  0xC8,
  0xCA,
};

if (process == 0x46 && _purchaseTerminals.contains(terminal)) {
  return TransitTransactionType.purchase;
}
```

단말 `CA`의 정확한 이름을 임의로 `편의점`, `자판기`, `POS` 등으로 표시하지 않는다. 목록에는 `물품 구매` 또는 `결제`만 표시한다.

### 18.3 권장 모델 보완

현재 `ParsedTransitHistory.usageDate`는 날짜만 보존한다. 물품 구매 기록은 바이트 6~7에 시각이 있으므로 향후 다음 중 하나를 권장한다.

- `DateTime? usageDateTime`으로 날짜와 시각을 함께 보존
- 또는 `Duration? transactionTimeOfDay` 같은 별도 필드 추가

1차 최소 수정에서는 유형만 `purchase`로 바로잡고, 시각 표시는 별도 변경으로 분리해도 된다. 원시 블록은 보존되므로 정보가 소실되지는 않는다.

### 18.4 필수 회귀 테스트

```text
raw: CA46000034E35DA49B0AE60000000900
type: purchase
date: 2026-07-03
time: 11:45:08 (시각 모델을 구현하는 경우)
balance: 230
must not resolve 9B-0A as railway stations
```

UI 테스트에서는 `CA/46`이 `유형 미확인`으로 표시되지 않고 `물품 구매` 또는 제품에서 선택한 `결제` 문구로 표시되는지 확인한다.

## 19. 후속 판단: 처리 코드 `0x46` 단독 분류 여부

이 앱은 시스템 코드 `0003`, 서비스 코드 `090F`의 정상적인 16바이트 이용이력만 파싱한다. 이 제한된 컨텍스트에서는 바이트 1의 처리 코드가 거래 의미를 나타내고, 바이트 0의 단말 코드는 거래를 수행한 장치 종류를 나타낸다.

공개된 복수의 역분석 자료에서 `0x46`은 일관되게 `物販`, 즉 교통 이용 외 전자머니 물품 결제로 해석된다. 실제 `CA/46` 샘플도 날짜 뒤 바이트가 승하차역이 아니라 유효한 시각 `11:45:08`로 해석되고, 처리 후 잔액이 기록된 물품 구매 레이아웃과 일치한다.

따라서 알려진 단말 집합 `{C7, C8, CA}`을 계속 늘리는 것보다 다음처럼 처리 코드 `46`을 기준으로 분류하는 편이 새로운 단말 변형에 강하다.

```dart
if (process == 0x46) {
  return TransitTransactionType.purchase;
}
```

다만 이 규칙은 임의의 FeliCa 데이터 전체가 아니라 다음 전제 안에서만 적용한다.

- 시스템 코드가 `0003`으로 검증됨
- 서비스 코드 `090F`에서 읽음
- 블록 길이가 정확히 16바이트임
- 빈 블록이나 통신 오류 응답이 아님
- 날짜 필드가 유효함

선택적으로 물품 구매 시각 필드를 검증할 수 있다.

```dart
bool hasValidPurchaseTime(List<int> bytes) {
  final packed = (bytes[6] << 8) | bytes[7];
  final hour = packed >> 11;
  final minute = (packed >> 5) & 0x3F;
  final second = (packed & 0x1F) * 2;
  return hour < 24 && minute < 60 && second < 60;
}
```

하지만 기존 앱이 물품 구매 시각을 모델링하지 않는다면 이 검증 때문에 정상 거래를 `unknown`으로 되돌릴 필요는 없다. 원본 통신과 날짜 검증이 정상이고 `process == 0x46`이면 `purchase`로 분류하는 것을 권장한다.

관련 코드를 혼동하지 않는다.

| 처리 코드 | 의미 |
|---|---|
| `0x46` | 물품 구매 |
| `0x4A` | 물품 구매 취소 |
| `0x4B` | 입장 물품 구매 계열 |
| `0xC6` | 현금 병용 물품 구매 계열 |
| `0xCB` | 입장·현금 병용 물품 구매 계열 |

이들은 모두 별도 처리 코드이므로 `46` 규칙에 잘못 포함되지 않는다. 취소·현금 병용 거래를 현재 enum의 `purchase`, `refund`, `adjustment` 중 어디에 배치할지는 실제 fixture 확보 후 별도 결정한다.

# 2차 수정안

> 구현 상태: 2026-08-12 완료. `phase2-parser-v3`에 반영했다. 실제 `17/01`과 `CA/46`을 회귀 fixture로 추가했으며, 물품 구매 시각의 모델·UI 표시는 이번 범위에서 보류했다.

## 20. 수정 목적과 범위

2차 수정은 새로 확보한 실제 카드 기록 두 건을 반영한다.

```text
1701000234DE44244428EC0400000300
CA46000034E35DA49B0AE60000000900
```

수정 목표:

1. `17/01` 간이 개찰기 철도 이용을 실제 fixture로 고정한다.
2. 물품 구매를 특정 단말 목록이 아니라 처리 코드 `46`으로 판정한다.
3. `CA/46`을 `unknown`이 아닌 물품 구매로 표시한다.
4. 물품 구매 레코드의 바이트 6~9를 역 코드로 해석하지 않는다.
5. 선택적으로 물품 구매 시각을 파싱할 수 있는 후속 기반을 남긴다.

이번 수정에서는 물품 구매 취소·현금 병용 코드와 점포명 해석은 구현하지 않는다.

## 21. 현재 코드 상태

현재 `TransitHistoryParser`의 개찰 단말 집합에는 이미 `0x17`이 포함되어 있다.

```dart
static const _conventionalRailGateTerminals = <int>{
  0x16,
  0x17,
  0x1A,
  0x1D,
};
```

따라서 `17/01` 지원 로직 자체는 이미 반영된 상태다. 2차 수정에서는 제공된 실제 원본을 회귀 테스트로 추가하고 역명 결과를 검증한다.

반면 물품 구매는 아직 다음처럼 단말 `C7`, `C8`만 허용한다.

```dart
if ((terminal == 0xC7 || terminal == 0xC8) && process == 0x46) {
  return TransitTransactionType.purchase;
}
```

이 조건 때문에 실제 `CA/46` 기록이 `unknown`으로 떨어진다.

## 22. 필수 코드 변경

### 22.1 물품 구매 분류

기존 단말 화이트리스트 조건을 제거하고 처리 코드로 분류한다.

변경 전:

```dart
if ((terminal == 0xC7 || terminal == 0xC8) && process == 0x46) {
  return TransitTransactionType.purchase;
}
```

변경 후:

```dart
if (process == 0x46) {
  return TransitTransactionType.purchase;
}
```

이 규칙은 이미 NFC 계층에서 검증된 시스템 코드 `0003`, 서비스 코드 `090F`, 정상 16바이트 블록 안에서만 실행된다.

### 22.2 파서 버전

분류 결과가 달라지므로 파서 버전을 증가시킨다.

```dart
static const version = 'phase2-parser-v3';
```

프로젝트의 버전 정책이 다르면 동등한 다음 버전을 사용한다.

### 22.3 물품 구매 시각

최소 수정에서는 시각 모델을 추가하지 않아도 된다. 원본은 `RawHistoryBlock`에 보존된다.

시각을 이번에 표시하기로 결정하면 물품 구매 레코드에서만 바이트 6~7을 다음처럼 해석한다.

```dart
final packedTime = (bytes[6] << 8) | bytes[7];
final hour = packedTime >> 11;
final minute = (packedTime >> 5) & 0x3F;
final second = (packedTime & 0x1F) * 2;
```

유효 범위:

```dart
hour < 24 && minute < 60 && second < 60
```

철도·버스 레코드에는 이 시각 파싱을 적용하지 않는다.

```text

```

| 필드 | 기대값 |
|---|---|
| 유형 | `purchase` |
| 단말 | `0xCA`, 세부 명칭 미확인 |
| 처리 | `0x46`, 물품 구매 |
| 날짜 | `2026-07-03` |

```text
물품 구매
```

제품 문구를 `결제`로 통일하기로 결정했다면 해당 문구를 사용해도 되지만, 기존 enum과 UI가 `물품 구매`를 사용하므로 2차 최소 수정에서는 기존 문구 유지가 안전하다.

`9B-0A`를 승차·하차역으로 조회하거나 표시하면 안 된다.

## 24. 금액 계산 주의사항

제공된 두 기록의 날짜와 잔액은 다음 순서다.

```text
2026-06-30 철도 이용 후 1,260엔
2026-07-03 물품 구매 후   230엔
```

두 기록이 원래 `090F` 배열에서도 바로 인접한다면 결제액은 `1,030엔`이다.

```text
1,260 - 230 = 1,030
```

두 기록 사이에 생략된 이력이 있다면 `1,030엔`을 결제액으로 확정하면 안 된다. 기존처럼 실제 배열에서 바로 다음의 더 오래된 레코드와 비교하는 규칙을 유지한다.

회귀 테스트에서는 실제 NFC 배열과 동일하게 최신 `CA/46`을 먼저, 더 오래된 `17/01`을 다음에 배치한다. 문서 20절의 원본 나열 순서를 그대로 파서 배열 순서로 사용하지 않는다.

## 29. `1A/06`: 개찰 창구 처리

### 29.1 JR 시나가와

```text
1A 06 00 0E | 35 02 | 01 07 | 01 07 | 7C 01 | 00 00 52 | 00
```

| 필드 | 값 |
|---|---|
| 단말 | `0x1A`, 개찰 단말 |
| 처리 | `0x06`, 개찰 창구 처리(改札窓口処理) |
| 날짜 | `2026-08-02` |
| 지역 | `0` |
| 처리 장소 코드 | `01-07` |
| 처리 장소 | JR 동일본 / 도카이도선 / 品川 |
| 처리 후 잔액 | `0x017C = 380엔` |
| 거래 순번 | `0x000052 = 82` |

사용자가 확인한 실제 행위는 **열차 승차가 아니라 시나가와역 개찰구 통과를 위한 지불·역무 처리**다. 두 코드 쌍이 모두 `01/07`인 것은 `品川 → 品川` 승차를 뜻하지 않고 동일한 처리 장소가 반복 기록된 것으로 본다.

권장 표시:

```text
개찰 창구 처리 · 시나가와
역무원 개찰 처리
```

피해야 할 표시:

```text
철도 이용 · 시나가와 → 시나가와
```

원본만으로 입장 정보 취소, 수동 운임 징수, 입·출장 상태 수정, 통과 정산 중 무엇인지 세분할 수 없다. 사용자의 실제 맥락을 별도로 저장하지 않는 앱에서는 `개찰 창구 처리`까지만 표시한다. `00 0E`의 세부 의미도 검증 전에는 추정하지 않는다.

## 30. `1B/02`: 모바일 충전

### 30.1 실제 모바일 충전 샘플 A

```text
1B 02 3F 00 | 35 03 | 02 FD | 00 00 | 3F 02 | 00 00 57 | 00
```

| 필드 | 값 |
|---|---|
| 단말 | `0x1B`, 휴대전화·모바일 단말 |
| 처리 | `0x02`, 충전 |
| 날짜 | `2026-08-03` |
| 처리 후 잔액 | `0x023F = 575엔` |
| 거래 순번 | `0x000057 = 87` |

### 30.2 실제 Mobile PASMO 충전 샘플

```text
1B 02 3F 00 | 34 96 | 9B 81 | 00 00 | 24 02 | 00 04 13 | 00
```

| 필드 | 값 |
|---|---|
| 단말/처리 | `1B/02`, 모바일 충전 |
| 날짜 | `2026-04-22` |
| 처리 후 잔액 | `0x0224 = 548엔` |

`1B/02`는 모바일 충전으로 분류한다. 동일 조합이 Mobile Suica와 Mobile PASMO에서 나타날 수 있으므로 원본 `090F` 한 건만으로 카드 브랜드를 판정하지 않는다. 카드 브랜드는 카드 식별 계층에서 이미 안전하게 확인된 경우에만 보조 문구로 사용한다.

바이트 6~9의 `02 FD 00 00`, `9B 81 00 00`을 역 코드로 조회하지 않는다. 모바일 충전 레이아웃의 내부 메타데이터로 보존하되 의미를 추정하지 않는다.

권장 표시:

```text
모바일에서 충전
```

|---|---|

## 32. `C8/C6`: 현금 병용 물품 구매

```text
C8 C6 00 00 | 34 2E | 55 41 | A9 F5 | 48 00 | 00 04 0E | 00
```

| 필드 | 값 |
|---|---|
| 단말 | `0xC8`, 판매·자판기 계열 단말 |
| 처리 | `0xC6`, 현금 병용 물품 구매(現金併用物販) |
| 일시 | `2026-01-14 10:42:02` |
| 점포·단말 코드 후보 | `A9-F5`; 정확한 상호 미확인 |
| 처리 후 잔액 | `0x0048 = 72엔` |
| 거래 순번 | `0x00040E = 1038` |

시각 계산:

```text
packed = 0x5541
hour   = packed >> 11          = 10
minute = (packed >> 5) & 0x3F = 42
second = (packed & 0x1F) * 2  = 2
```

권장 분류는 `purchase`이며, 별도 세부 유형 또는 보조 문구로 `현금 병용`을 표시한다.

```text
물품 구매 · 현금 병용
```

교통카드 잔액 사용분, 현금 사용분, 전체 구매액은 이 기록 하나로 확정하지 않는다. 점포명과 상품명도 추정하지 않는다. 바이트 6~9에 역 조회를 수행하면 안 된다.

2차 수정의 `process == 0x46` 규칙과는 별도로 `0xC6`을 명시적으로 추가해야 한다. `C6`은 `46`과 값이 다른 독립 처리 코드다.

## 33. `1A/02`: 역 개찰 단말 충전

```text
1A 02 00 00 | 34 2C | E9 1F | 00 00 | 9F 04 | 00 04 04 | C0
```

| 필드 | 값 |
|---|---|
| 단말 | `0x1A`, 개찰 단말 |
| 처리 | `0x02`, 충전 |
| 날짜 | `2026-01-12` |
| 정규화 지역 | `3` |
| 처리 장소 코드 | `03-E9-1F` |
| 처리 장소 | 福岡市交通局 / 七隈線 / 天神南 |
| 처리 후 잔액 | `0x049F = 1,183엔` |
| 거래 순번 | `0x000404 = 1028` |

`E9/1F`는 승차역이 아니라 충전 처리 장소다. `1A`이므로 자동발권기라고 표시하지 않고 `역 개찰 단말 충전`으로 구분한다.

권장 표시:

```text
충전 · 텐진미나미역
역 개찰 단말에서 충전
```

## 34. 버스 실제 사업자 매핑

### 34.1 후쿠오카: 西日本鉄道

```text
05 0F 00 0F | 34 2E | 0A 01 | 00 00 | 30 00 | 00 04 12 | C0
```

| 필드 | 값 |
|---|---|
| 단말/처리 | `05/0F`, 버스 이용 |
| 날짜 | `2026-01-14` |
| 정규화 지역 | `3` |
| 사업자·노선 식별부 | `0A-01` |
| 실제 사업자 | 西日本鉄道 |
| 처리 후 잔액 | `0x0030 = 48엔` |
| 거래 순번 | `0x000412 = 1042` |

사용자의 실제 이용 맥락으로 `西日本鉄道`을 확인했다. 앱 내부 매핑은 다음 전체 시그니처에 한해 적용한다.

```text
region=3 + terminal=05 + process=0F + bytes[6..7]=0A01
→ 西日本鉄道
```

`0A01`만 단독 전역 키로 사용하거나 모든 후쿠오카권 버스를 니시테쓰로 표시하지 않는다. 니시테쓰 버스 자회사와 다른 nimoca 참여 사업자는 별도 fixture가 필요하다.

### 34.2 나고야: 名古屋市交通局 市バス

```text
05 0D 00 0F | 34 E2 | 0D 2A | 00 00 | 1A 04 | 00 00 04 | 40
```

| 필드 | 값 |
|---|---|
| 단말/처리 | `05/0D`, 버스 이용 |
| 날짜 | `2026-07-02` |
| 정규화 지역 | `1` |
| 사업자·노선 식별부 | `0D-2A` |
| 실제 사업자 | 名古屋市交通局 市バス |
| 처리 후 잔액 | `0x041A = 1,050엔` |
| 거래 순번 | `0x000004 = 4` |

앱 내부 매핑은 다음 전체 시그니처에 한해 적용한다.

```text
region=1 + terminal=05 + process=0D + bytes[6..7]=0D2A
→ 名古屋市交通局 市バス
```

`05/0D` 전체를 나고야 시영버스로 분류하거나 `0D2A`만 지역 구분 없이 전역 사업자 키로 사용하면 안 된다. `0D`와 `0F`는 모두 버스 계열 처리 코드이며 그 자체가 사업자 코드는 아니다.

## 35. 권장 분류 및 레이아웃 규칙

### 35.1 거래 유형

실제 fixture로 확인된 최소 규칙:

```dart
if (terminal == 0x1A && process == 0x06) {
  return TransitTransactionType.gateWindowProcessing; // 새 유형명 예시
}

if (process == 0x02 &&
    const <int>{0x08, 0x1A, 0x1B}.contains(terminal)) {
  return TransitTransactionType.charge;
}

if (terminal == 0x1B && process == 0x48) {
  return TransitTransactionType.charge;
}

if (terminal == 0xC8 && process == 0xC6) {
  return TransitTransactionType.purchase;
}

if (terminal == 0x05 && (process == 0x0D || process == 0x0F)) {
  return TransitTransactionType.bus;
}
```

`gateWindowProcessing`은 예시 이름이다. 기존 도메인에 `adjustment`처럼 충분히 명확한 유형이 있다면 이를 재사용할 수 있지만 사용자 문구는 `개찰 창구 처리`로 구체화한다. `rail`로 재사용해서는 안 된다.

### 35.2 바이트 6~9 해석

| 거래 레이아웃 | 바이트 6~9 처리 |
|---|---|
| 일반 철도 `.../01` | 승차 노선·역 + 하차 노선·역 |
| 개찰 창구 `1A/06` | 동일 역 코드가 반복될 수 있는 처리 장소 |
| 역 충전 `08/02`, `1A/02` | 첫 코드 쌍을 충전 처리 장소로 사용 |
| 모바일 충전 `1B/02`, `1B/48` | 내부 메타데이터; 역 조회 금지 |
| 버스 `05/0D`, `05/0F` | 버스 사업자·노선·정류장 계열 데이터; 철도역 조회 금지 |
| 물품 구매 `46`, `C6` | 바이트 6~7은 시각, 8~9는 점포·단말 계열; 역 조회 금지 |

거래 유형보다 먼저 바이트 6~9를 철도역으로 해석하면 모바일 충전, 버스, 물품 구매에서 허위 역명이 생길 수 있다. 먼저 유형을 판정한 뒤 해당 레이아웃만 해석한다.

### 35.3 버스 사업자 표시

버스 사업자 매핑 키는 최소한 다음 필드를 포함한다.

```dart
typedef BusOperatorKey = ({
  int regionCode,
  int terminalCode,
  int processCode,
  int byte6,
  int byte7,
});
```

현재 확인된 두 매핑 외에는 `버스 이용`으로만 표시하고 사업자명은 `확인할 수 없음`으로 둔다.

## 41. 실제 샘플 A: `21/02` 역 단말 충전

원본:

```text
21 02 00 00 | 35 0D | AC 38 | 00 00 | 7B 17 | 00 00 5E | 40
```

| 필드 | 값 |
|---|---|
| 단말 | `0x21`, 정확한 공개 단말 명칭 미확인 |
| 처리 | `0x02`, 충전 |
| 날짜 | `2026-08-13` |
| 정규화 지역 | `1`, 중부권 |
| 바이트 6~7 | `AC-38`; 이 fixture에서 정확한 의미·장소 미확인 |
| 처리 후 잔액 | `0x177B = 6,011엔` |
| 거래 순번 | `0x00005E = 94` |
| 사용자 확인 실제 행위 | 지하철역에서 5,000엔 충전 |

### 41.1 현재 앱의 원인

현재 충전 분류는 처리 코드가 `02`여도 단말이 `08`, `1A`, `1B` 중 하나일 때만 허용한다.

```dart
if (process == 0x02 &&
    (terminal == 0x08 || terminal == 0x1A || terminal == 0x1B)) {
  return TransitTransactionType.charge;
}
```

따라서 실제 `21/02`는 `unknown`으로 떨어진다. 처리 장소 코드도 현재 `08/02`, `1A/02`에서만 만들기 때문에 `21/02`에는 생성되지 않는다.

### 41.2 권장 분류 수정

시스템 코드 `0003`, 서비스 코드 `090F`, 정상 16바이트 블록이라는 기존 검증 경계 안에서는 처리 코드 `02`를 충전으로 분류한다.

```dart
if (process == 0x02) {
  return TransitTransactionType.charge;
}
```

유형은 처리 코드로 정하고, 충전 방식은 단말 코드로 구분한다.

| 조합 | 권장 사용자 문구 | 확신 수준 |
|---|---|---|
| `08/02` | 자동발권기에서 충전 | 기존 실제 fixture 확인 |
| `1A/02` | 역 개찰 단말에서 충전 | 기존 실제 fixture 확인 |
| `1B/02` | 모바일에서 충전 | 기존 실제 fixture 확인 |
| `21/02` | 역 단말에서 충전 | 이번 실제 fixture의 사용자 맥락 확인; 정확한 기기 명칭 미확인 |
| 기타 `*/02` | 카드 충전 | 처리 의미만 확정, 방식 미확인 |

`0x21`을 공개 근거 없이 `지하철 자동발권기`, `정산기` 등으로 구체화하지 않는다. 내부 단말 명칭은 `미확인 역 단말` 또는 이에 준하는 보수적인 값으로 둔다.

### 41.3 장소 코드 주의

이 기록의 `AC-38`은 현재 번들 DB에서 지역 `1`의 名古屋鉄道 空港線 中部国際空港과 일치한다. 그러나 사용자가 확인한 맥락은 `지하철역에서 충전`이며 정확한 역명은 아직 제공되지 않았다.

따라서 이번 수정에서 `21/02`의 바이트 6~7을 무조건 일반 철도역 처리 장소로 표시하면 안 된다. 정확한 충전역 또는 `21/02` 레이아웃의 공개 근거가 확보될 때까지 다음처럼 처리한다.

```text
유형: 충전
방식: 역 단말
장소: 확인할 수 없음
원시 AC-38: 내부 원본에만 보존
```

### 41.4 5,000엔 계산

이 블록 자체가 저장하는 값은 처리 후 잔액 `6,011엔`이다. 바로 인접한 더 오래된 기록의 잔액이 `1,011엔`일 때만 충전액 `5,000엔`을 계산한다.

```text
6,011 - 1,011 = 5,000엔
```

인접한 오래된 기록이 없거나 다른 거래가 생략됐다면 사용자 확인 맥락과 별개로 앱 계산 금액은 `확인할 수 없음`을 유지한다.

## 44. 게이오선으로 잘못 해석되는 원인

현재 번들 `yoiko_station_codes.csv`에는 다음 데이터가 없다.

```text
伊予鉄道: 0건
古町: 0건
梅津寺: 0건
松山市: 0건
region=3 + line=C5: 0건
```

반면 지역 `0`에는 같은 `C5` 노선 코드를 사용하는 京王電鉄 京王線 데이터가 있다.

```text
00-C5-1B → 京王線 / 聖蹟桜ヶ丘
00-C5-17 → 京王線 / 東府中
```

파서는 두 실제 철도 기록의 지역을 이미 정상적으로 `3`으로 추출한다. 문제는 지역 파싱이 아니라 역 DB 조회기의 폴백이다.

현재 조회 순서:

1. `region + line + station` 정확 조회
2. 지역 힌트 조회
3. 지역을 버리고 `line + station` 전국 후보 조회
4. 전국 후보가 하나이면 다른 지역이라도 확정

그 결과:

```text
03-C5-1B → 지역 3 미등록 → 전국 C5-1B 하나 → 聖蹟桜ヶ丘 오매핑
03-C5-27 → 지역 3 미등록 → 전국 후보 없음 → 역 정보 미등록
03-C5-17 → 지역 3 미등록 → 전국 C5-17 하나 → 東府中 오매핑
```

## 45. 지역 폴백 수정안

정규화된 지역 코드 `0~3`이 존재하는 철도 기록에서는 다른 지역의 동일 `line + station` 코드를 자동 확정하지 않는다.

권장 원칙:

```text
지역 0~3 + 정확 일치 있음
→ 정확한 역 반환

지역 0~3 + 정확 일치 없음
→ 역 정보 미등록 또는 같은 지역 후보만 반환

지역 자체가 미확인 sentinel
→ 전국 line + station 후보 검색 허용
```

구현 예시:

```dart
final hasNormalizedRegion = requestedCode.regionCode >= 0 &&
    requestedCode.regionCode <= 3;

if (hasNormalizedRegion) {
  return StationResolution(
    requestedCode: requestedCode,
    strategy: StationMatchStrategy.notFound,
  );
}

// 지역을 모르는 입력에만 전국 line + station 폴백 수행
```

기존 `0xFE` 같은 지역 미확인 sentinel의 trip-context 조회는 유지할 수 있다. 레거시 원시 지역값 `50`, `F0`을 resolver에 직접 전달하는 경로가 있다면 먼저 정규화한 뒤 동일 원칙을 적용한다.

보완 역 데이터를 추가하더라도 이 폴백 수정은 반드시 함께 수행한다. 그렇지 않으면 아직 보완되지 않은 다른 지역 `3` 역이 계속 수도권 역으로 오매핑될 수 있다.

### 46.1 실제 fixture로 확인된 역

### 46.2 공식 역 순서와 코드 연속 패턴으로 추론한 역

확인된 세 코드에는 역 한 칸마다 코드가 `+2` 되는 동일 패턴이 성립한다.

```text
松山市 17 → 大手町 19 → 古町 1B

古町 1B → 衣山 1D → 西衣山 1F → 山西 21
          → 三津 23 → 港山 25 → 梅津寺 27
```

이요테츠 공식 역 순서는 다음과 같다.

```text
高浜－梅津寺－港山－三津－山西－西衣山－衣山－古町－大手町－松山市
```

따라서 전체 보완 후보는 다음과 같다.

| 전체 코드 | 사업자 | 노선 | 역명 | 근거 수준 |
|---|---|---|---|---|
| `03-C5-17` | 伊予鉄道 | 高浜線 | 松山市 | `verified_fixture` |
| `03-C5-19` | 伊予鉄道 | 高浜線 | 大手町 | `inferred_sequence` |
| `03-C5-1B` | 伊予鉄道 | 高浜線 | 古町 | `verified_fixture` |
| `03-C5-1D` | 伊予鉄道 | 高浜線 | 衣山 | `inferred_sequence` |
| `03-C5-1F` | 伊予鉄道 | 高浜線 | 西衣山 | `inferred_sequence` |
| `03-C5-21` | 伊予鉄道 | 高浜線 | 山西 | `inferred_sequence` |
| `03-C5-23` | 伊予鉄道 | 高浜線 | 三津 | `inferred_sequence` |
| `03-C5-25` | 伊予鉄道 | 高浜線 | 港山 | `inferred_sequence` |
| `03-C5-27` | 伊予鉄道 | 高浜線 | 梅津寺 | `verified_fixture` |
| `03-C5-29` | 伊予鉄道 | 高浜線 | 高浜 | `inferred_sequence` |

추론값은 세 실제 앵커와 공식 역 순서에 모두 부합하므로 신뢰도가 높지만, 실제 카드 fixture로 직접 확인된 값처럼 문서화하면 안 된다. 향후 해당 역의 실제 기록을 확보할 때 `inferred_sequence`에서 `verified_fixture`로 승격한다.

### 46.3 데이터 저장 권장안

기존 Yoiko CSV는 허가된 원본 데이터와 출처를 유지해야 하므로 사용자 fixture와 추론값을 같은 출처로 위장해 직접 삽입하지 않는다. 별도 보완 데이터 파일 또는 명시적인 override 계층을 권장한다.

예시:

```text
assets/data/stations/verified_station_overrides.csv
```

권장 필드:

```text
region,line,station,operator,line_name,station_name,evidence,source_note
3,197,23,伊予鉄道,高浜線,松山市,verified_fixture,user-provided 090F
3,197,25,伊予鉄道,高浜線,大手町,inferred_sequence,official order + step-2 sequence
```

위 예시는 십진 CSV 저장 형식을 가정한다. `C5=197`, `17=23`, `19=25`처럼 변환한다. 실제 파일 스키마는 기존 로더와 맞추되 `evidence`와 `source_note`를 잃지 않는다.

병합 우선순위:

1. 동일 전체 코드의 검증된 앱 보완 데이터
2. 기존 허가된 Yoiko 데이터
3. 정확 지역에서 모두 미등록이면 `notFound`

추론값을 사용자에게 별도 경고로 표시할 필요까지는 없지만, 코드와 데이터 파일에는 근거 수준을 유지한다.

## 47. 권장 구현 변경

### 47.1 파서

- `process == 0x02`를 정상 `090F` 컨텍스트에서 충전으로 분류한다.

- 이요테츠 高浜線 보완 데이터 10건을 별도 출처로 병합한다.

- 기존 지역 `0`의 京王線 `C5` 데이터는 변경하지 않는다.

### 47.3 UI

- `21/02`: `역 단말에서 충전`

- 지역 `3` 미등록 역에 京王線 역명을 표시하지 않는다.

## 54. 보수적인 사업자 매핑

현재는 이요테츠 버스 실제 fixture가 없어서 `0F3D`가 다음 중 무엇인지 구분할 수 없다.

- 이요테츠 시내전차 전용 식별값
- 이요테츠 버스와 시내전차가 공유하는 사업자 식별값
- 노선·차량 정보를 일부 포함하는 복합 식별값

```text

terminal=05
process=0D
bytes[6..7]=0F3D
→ operatorName: 伊予鉄道
→ specificMode: unknown
```

권장 UI:

```text

伊予鉄道
```

제품의 현재 상위 유형이 `bus` 하나뿐이라면 유형명은 기존 `버스 이용`을 유지할 수 있지만, 사업자 보조 문구에는 `伊予鉄道`만 표시한다. 이 경우에도 상세 화면에서 `노면전차` 또는 `伊予鉄バス`로 확정해서는 안 된다.

```text

伊予鉄バス
노면전차 이용
버스 이용 · 伊予鉄バス
```

이번 사용자의 실제 행위는 노면전차였지만, 그 맥락을 모든 동일 코드 기록의 교통수단 판정으로 일반화하지 않는다.

## 55. 기존 버스 사업자 매핑과의 관계

기존의 사업자 매핑과 동일하게 지역·단말·처리·바이트 6~7 전체를 키로 사용한다.


```text

region=3 + 05/0D → 伊予鉄道
0F3D → 모든 지역에서 伊予鉄道
```

## 62. 새로 확인된 `C5` 코드의 성격

4차 수정에서는 실제 高浜線 fixture를 근거로 다음처럼 보완했다.

- 郡中線
- 横河原線

## 64. 松山市 공통역 모델 문제

현재 보완 데이터는 `03-C5-17`을 다음처럼 저장한다.

```text
伊予鉄道 / 高浜線 / 松山市
```

이 구조를 그대로 유지하면서 `03-C5-01 → 03-C5-17`을 조회하면 목적지 松山市에 高浜線이 붙어 郡中線 경로와 충돌할 수 있다.

또한 동일 전체 코드 `03-C5-17`을 다음처럼 중복 추가하는 방식도 권장하지 않는다.

```text
03-C5-17 / 高浜線 / 松山市
03-C5-17 / 郡中線 / 松山市
03-C5-17 / 横河原線 / 松山市
```

현재 resolver는 동일 전체 코드의 서로 다른 `lineName` 레코드를 복수 후보로 취급하므로, 하나의 물리적 역이 불필요하게 `multipleCandidates`가 될 수 있다.

권장 모델:

```text
역 식별:
03-C5-17 → 伊予鉄道 / 松山市

소속 노선:
高浜線, 郡中線, 横河原線

실제 이용 노선:
승하차 코드 쌍을 통해 별도 결정
```

현재 `StationRecord`가 단일 `lineName`만 지원한다면 최소 수정으로 松山市의 데이터 노선명을 `伊予鉄道郊外電車` 같은 공통값으로 바꾸고, 목록·상세의 이용 노선은 `ResolvedStationPair` 또는 별도 경로 resolver에서 계산한다.

## 65. 경로 컨텍스트 기반 노선 판정

현재 실제 fixture로 검증 가능한 최소 규칙은 다음과 같다.

```text
두 역 모두 지역 3, 노선 코드 C5

두 역 코드가 01~17 범위이고
적어도 하나가 01~15
→ 郡中線

두 역 코드가 17~29 범위이고
적어도 하나가 19~29
→ 高浜線

두 역이 모두 17
→ 노선 미확인

한 역이 01~15이고 다른 역이 19~29
→ 단일 노선으로 단정하지 않음; 환승 또는 데이터 추가 확인 필요

그 외 C5 코드
→ 실제 横河原線 fixture 확보 전 노선 추정 금지
```

Dart 형태의 예시:

```dart
String? resolveIyotetsuLine({
  required int region,
  required int boardingLine,
  required int boardingStation,
  required int alightingLine,
  required int alightingStation,
}) {
  if (region != 0x03 || boardingLine != 0xC5 || alightingLine != 0xC5) {
    return null;
  }

  final stations = {boardingStation, alightingStation};
  final isGunchuRange = stations.every((code) => code >= 0x01 && code <= 0x17);
  if (isGunchuRange && stations.any((code) => code <= 0x15)) {
    return '郡中線';
  }

  final isTakahamaRange = stations.every((code) => code >= 0x17 && code <= 0x29);
  if (isTakahamaRange && stations.any((code) => code >= 0x19)) {
    return '高浜線';
  }

  return null;
}
```

이 규칙은 현재 실제 fixture가 있는 郡中線과 高浜線에만 적용한다. `C5` 전체를 두 노선 중 하나로 억지 분류하지 않는다.

## 66. 거래 금액 주의사항

앞서 제공된 이요테츠 차량 단말 기록의 거래 순번 필드는 `79`, 이번 철도 기록은 `81`이다.

```text
순번 79: 처리 후 잔액 1,839엔
순번 81: 처리 후 잔액 1,279엔
```

초기 구현에서는 이 값을 항상 1씩 증가하는 이용내역 개수로 해석했으나, 실제 카드에서 최신순으로 `34 → 32 → 30 → 2E`처럼 2씩 변하는 정상 기록이 확인되었다. 기존 카드 fixture에도 `129 → 127`처럼 차이가 1이 아닌 정상 인접 기록이 있다. 따라서 `현재 값 = 이전 값 + 1` 조건으로 이용내역 누락 여부를 판정해서는 안 된다.

앱은 NFC 서비스 `090F`에서 실제로 연속해서 읽은 두 블록의 잔액 차이를 기존 방식대로 계산한다. 이 필드는 원본·진단 정보로 파싱할 수 있지만 현재 금액 계산의 차단 조건으로 사용하지 않는다.

## 67. 권장 구현 변경

### 역 보완 데이터

- `03-C5-01` 郡中港을 `verified_fixture`로 추가한다.
- `03-C5-03`부터 `03-C5-15`까지 郡中線 중간 10개 역을 `inferred_sequence`로 추가한다.

### 도메인·resolver

- 역의 물리적 식별과 실제 이용 노선 판정을 분리한다.
- `ResolvedStationPair`에 nullable 이용 노선명 또는 동등한 경로 결과를 추가하는 방안을 우선 검토한다.
- 동일한 松山市역을 노선별 중복 역 후보로 만들지 않는다.
- 실제 승하차 쌍이 郡中線 범위일 때만 `郡中線`을 반환한다.
- 현재 검증되지 않은 横河原線 코드는 추정하지 않는다.

### UI

- 실제 원본을 `郡中港 → 松山市`로 표시한다.
- 경로 보조 문구를 `伊予鉄道 · 郡中線`으로 표시한다.
- 목적지 松山市에 `高浜線`을 고정 표시하지 않는다.
- 역별 상세에서 단일 노선만 표시해야 하는 기존 UI라면 松山市에는 공통값을 사용하고, 이용 노선은 경로 요약에서만 표시한다.

### 파서 버전

원시 거래 유형 자체는 기존 `16/01 = rail`과 동일하다. 그러나 해석 결과와 UI 노선명이 달라지므로 캐시나 오류 제보에 파서 버전이 사용된다면 버전을 증가시킨다.

## 71. 4-2차 수정 구현 결과

- 파서 버전을 `phase2-parser-v6.1`로 올리고 원본 바이트 12~14의 거래 순번 필드는 진단 정보로 파싱한다.
